# 基于 MBSE 的专利代理流程

## 项目简介

本项目将 Model-Based Systems Engineering（MBSE，基于模型的系统工程）引入专利代理工作，用结构化模型连接技术交底、权利要求撰写、说明书编制、新颖性与创造性分析、审查意见答复以及后续的版本和质量治理。

核心目标不是用模型自动替代专利代理师，而是把原本依赖自然语言、个人经验和隐性知识的专利代理过程，转换为：

- 对象明确；
- 关系清晰；
- 证据可定位；
- 权利要求与技术方案可相互追溯；
- 修改影响可识别；
- 审查意见答复可复核；
- 团队协作和知识传承可持续。

本项目适用于机械结构、电子通信、人工智能、软件算法、化学材料和生物技术等技术领域。

## 二、MBSE 的核心模型

本项目使用 `R/F/S/B/E` 五层模型表达技术方案。

| 层级 | 含义 | 主要问题 |
|---|---|---|
| `R` | Requirement，技术需求或待解决问题 | 要解决什么技术问题？ |
| `F` | Function，技术功能 | 系统需要完成什么功能？ |
| `S` | Structure，技术结构 | 由哪些部件、模块、数据、材料或步骤实现？ |
| `B` | Behavior，技术行为 | 按什么顺序、条件、状态或触发关系运行？ |
| `E` | Effect，技术效果 | 通过哪些结构和行为产生何种技术效果？ |

基本链路如下：

```text
R：技术需求或技术问题
    ↓
F：功能、输入、技术变换、直接输出
    ↓
S：部件、模块、数据、材料、步骤及其连接
    ↓
B：顺序、状态、触发、控制、异常和交互
    ↓
E：具有证据基础的技术效果
```

在建模过程中，应保持以下基本闭环：

```text
R_problem
→ F<Input, Transformation, Output>
→ S/B/STATE
→ OutputState
→ E
```

需要特别注意：

- `F` 表示功能过程，不等于最终技术效果；
- `F.Output` 表示功能的直接输出；
- `E` 表示由具体结构、行为和关系产生的技术效果；
- 只有“提高效率”“提高准确率”等结果性描述，不能自动视为完整技术效果；
- 每个决定性效果都应尽量说明受影响对象、技术属性、产生条件、因果路径和证据来源。

## 三、专利代理形式化框架

本项目将专利代理形式化框架分为两个部分。

### 1. 业务核心模型：`PAF_core`

```text
PAF_core
= <ObjectContract,
   RelationContract,
   EvidenceContract,
   NormContract>
```

`PAF_core`用于第二至第五阶段的业务分析，主要回答：

- 处理什么技术对象；
- 对象之间有什么关系；
- 技术事实和法律主张来自何处；
- 应当按照什么法律和业务条件进行判断。

### 2. 治理扩展模型：`PAF_gov`

```text
PAF_gov
= <VersionContract,
   GovernanceContract>
```

`PAF_gov`主要用于：

- 版本基线；
- 版本替代；
- 变更影响传播；
- 审核状态；
- 角色权限；
- 责任记录；
- 操作留痕；
- AI 工具使用控制；
- 模型化复核记录；
- 经验规则和组织学习。

完整框架表示为：

```text
PAF = <PAF_core, PAF_gov>
```

其中：

- 第二至第五阶段重点处理业务模型；
- 版本、审核、责任和可审计性作为治理扩展集中处理；
- 治理记录不能替代技术事实证据；
- 操作日志不能替代技术交底、图纸、实验数据或申请文件原文。

## 四、九阶段基本流程

## 阶段1：技术交底与 MBSE 建模

### 输入

- 技术交底书；
- 产品结构图或系统框图；
- 工艺流程、控制流程或软件流程；
- 实验数据、测试数据或性能数据；
- 现有技术背景；
- 发明人补充说明。

### 处理内容

将技术材料转换为：

```text
R/F/S/B/E
```

并补充：

- 系统边界；
- 接口对象；
- 数据流或能量流；
- 参数和约束；
- 时序和状态；
- 异常路径；
- 技术效果及其证据。

### 输出

- 技术事实模型；
- R/F/S/B/E 节点表；
- 技术关系表；
- 接口和约束视图；
- 技术效果证据表；
- 待确认问题清单；
- 可检索技术要素。

---

## 阶段2：查新检索与保护单元筛选

查新检索不直接把关键词相似性当成专利结论，而是根据 MBSE 模型拆解检索要素。

### 检索要素来源

- `R`：技术问题、技术目标和应用场景；
- `F`：核心功能和技术变换；
- `S`：部件、模块、材料、数据结构和步骤；
- `B`：时序、状态、控制、触发和异常行为；
- `E`：技术效果、性能指标和比较基线；
- `REL`：位置、连接、依赖、流向、作用和顺序关系；
- `CT`：参数、范围、材料、环境、协议和逻辑条件。

### 保护单元筛选

每个候选保护单元应至少检查：

1. 是否具有明确技术对象；
2. 是否具有功能或技术作用；
3. 是否能够连接到技术问题；
4. 是否具有原始披露依据；
5. 是否能够形成技术效果或实施价值；
6. 是否能够独立进入权利要求层级；
7. 是否与其他特征具有明确组合关系。

找不到来源、功能作用或效果路径的内容，不应仅因为属于技术细节就直接包装为有效区别特征。

### 输出

- 查新检索块；
- 候选对比文件清单；
- 保护单元清单；
- 核心保护单元；
- 备选保护单元；
- 排除内容台账；
- 技术事实与现有技术对照表。

---

## 阶段3：权利要求书撰写

### 1. 技术模型到权利要求语义

MBSE 技术模型通过以下对象转换为权利要求语义：

| MBSE对象 | 权利要求语义对象 |
|---|---|
| `S` | `CF`，技术特征单元 |
| `REL` | 必要关系 |
| `B` | 顺序、状态、触发和行为限定 |
| `CV` | `CT`，权利要求约束单元 |
| `S/B/E`共同作用 | `INT`，相互作用组 |
| 原始技术来源 | 说明书和附图支持位置 |

权利要求语义可以表示为：

```text
Sem(C)
= <OBJ(C), CF(C), REL(C), CT(C), INT(C)>
```

其中：

- `OBJ(C)`：权利要求主题和客体类别；
- `CF(C)`：对象、结构、动作或功能型技术特征；
- `REL(C)`：连接、位置、作用、依赖、触发和顺序关系；
- `CT(C)`：参数、范围、材料、环境、协议、时序或逻辑约束；
- `INT(C)`：功能上相互支持、共同产生技术效果的特征组合。

### 2. 独立权利要求

独立权利要求应围绕主创新链构建：

```text
R*
→ F*
→ S*
→ B*
→ E*
```

写入独立权利要求的特征，应重点考虑：

- 是否为解决技术问题所必需；
- 是否对技术效果产生实际作用；
- 是否具有说明书和附图支持；
- 是否存在明确的结构、功能或行为关系；
- 是否影响保护范围；
- 是否能够抵御主要现有技术攻击。

### 3. 从属权利要求

从属权利要求不是独立的孤立特征清单，而是：

```text
上位权利要求全部限定
+
本项附加限定
```

其有效语义可以表示为：

```text
Sem_eff(Cc;q)
= Sem(Croot)
  ⊕ ΔSem(C1)
  ⊕ …
  ⊕ ΔSem(Cc)
```

其中：

- `q`：从独立权利要求到目标从属权利要求的合法引用路径；
- `ΔSem`：相对于直接上位权项新增或细化的语义单元；
- `⊕`：保持对象、关系、条件、顺序和相互作用语境的限制性组合。

从属权利要求的技术模型具有以下关系：

```text
模型限定：
U_eff(从权) ⊇ U_eff(上位权项)

保护范围：
Scope(从权) ⊆ Scope(上位权项)
```

也就是说：

- 随着从属层级增加，模型节点和关系可能不断累积；
- 但法律保护范围应逐级收缩；
- 增加模型节点不等于保护范围扩大；
- 增加附加特征也不当然等于创造性贡献增加。

从权增量通常包括四类：

1. 对既有节点的结构、材料、数据或步骤细化；
2. 对既有链路、参数、顺序或条件进行收缩；
3. 与继承特征形成相互作用或协同效果；
4. 与主链耦合的异常处理、校准、安全或替代分支。

从权增量子链不必独立重复完整的 `R/F/S/B/E` 五层，但增量子链与继承网络组合后必须闭合。

多项从属权利要求应当按每一条择一引用路径分别建模：

```text
独权 → 从权2 → 本项
独权 → 从权4 → 本项
```

不得把从权2和从权4的全部限定取并集，形成原权利要求文本中不存在的新组合。

### 输出

- 独立权利要求草案；
- 从属权利要求草案；
- 从权引用路径表；
- 独权—从权增量追溯账本；
- 从权反向验证矩阵；
- 权利要求—说明书—附图支持矩阵；
- 修改基础包。

## 阶段4：背景技术撰写

背景技术应说明：

- 所属技术领域；
- 现有技术的基本方案；
- 现有技术存在的技术问题；
- 为什么需要提出新的技术方案；
- 必要时引用相关现有技术文件。

背景技术不应：

- 夸大现有技术缺陷；
- 把未经检索证实的内容写成唯一现有技术；
- 预先泄露本申请的核心解决手段；
- 使用商业宣传性语言；
- 直接复制尚未核实的技术判断。

---

## 阶段5：具体实施方式撰写

具体实施方式应当能够支持权利要求中的技术特征、关系、参数、步骤和效果。

通常应包括：

- 系统或装置整体结构；
- 各部件或模块的功能；
- 部件之间的连接关系；
- 数据、能量或信号流；
- 工作流程和时序；
- 参数范围和适用条件；
- 异常处理和替代实施方式；
- 技术效果及其产生路径；
- 必要的实验、测试或比较结果。

对于电子通信、人工智能和软件方案，还应说明：

- 输入数据；
- 数据预处理；
- 算法或模型结构；
- 训练或推理步骤；
- 输出数据；
- 模型与具体应用场景的结合方式；
- 技术效果如何由算法特征与技术特征共同产生。

对于化学、材料和生物方案，还应说明：

- 组分及含量范围；
- 制备步骤；
- 工艺条件；
- 材料结构；
- 性能指标；
- 结构、工艺与性能之间的关系；
- 重复实施所需的必要条件。

## 阶段6：附图 Markdown 生成（可选）

可根据技术领域生成：

- 系统结构图；
- 模块连接图；
- 流程图；
- 时序图；
- 状态图；
- 数据流图；
- 工艺流程图；
- 结构剖视图；
- 关键部件放大图。

附图应满足：

- 标号与说明书一致；
- 同一部件在不同附图中使用同一标号；
- 附图中的标号能够回溯到技术特征；
- 不使用未经材料支持的结构；
- 不通过示意图比例推导未披露的精确尺寸；
- 图中不加入不必要的商业说明。

## 阶段7：VSDX 图纸制作与验收（可选）

当项目需要可编辑工程图时，可进一步生成 Visio/VSDX 文件。

重点验收：

- 部件是否发生错位或重叠；
- 标号是否清晰；
- 结构关系是否与说明书一致；
- 图纸是否能够反向支持权利要求；
- 导出 PNG、SVG 或 PDF 后版式是否稳定。

## 阶段8：既有申请文件审计与补强

对已经形成的申请文件进行反向检查。

### 审计内容

- 权利要求是否覆盖核心技术方案；
- 独立权利要求是否包含必要技术特征；
- 从属权利要求是否正确继承上位限定；
- 从权附加特征是否具有明确锚点；
- 权利要求中的关系、顺序和条件是否被保留；
- 说明书是否支持权利要求中的每项限定；
- 附图、说明书和权利要求的术语是否一致；
- 技术效果是否能够回溯到结构和行为；
- 是否存在无来源组合；
- 是否存在说明书有记载但权利要求没有表达的关键贡献；
- 是否存在仅有结果描述而缺少技术手段的特征。

### 基本验证方式

```text
从权利要求文本反向重建模型
→ 与技术交底模型比较
→ 与说明书支持位置比较
→ 与附图和标号比较
→ 识别缺失、冲突、漂移和无锚点限定
```

审计结果用于发现风险，不自动推出授权、无效或创造性结论。

## 阶段9：审查意见答复与驳回复审

收到审查意见后，首先将审查员主张拆分为可核实单元：

- 对比文件事实；
- 区别特征；
- 技术效果；
- 实际解决的技术问题；
- 问题是否在申请日前可被发现；
- 是否存在技术启示；
- 是否存在合理成功预期；
- 是否能够整体到达权利要求方案；
- 效果证据是否支持。

随后将每项主张标记为：

```text
支持
部分支持
不支持
无记载
待核实
```

答复路径可以包括：

- 事实错误；
- 证据定位错误；
- 关系遗漏；
- 顺序或状态遗漏；
- 技术问题确定不当；
- 问题发现贡献；
- 无来源桥接；
- 融合路径不成立；
- 缺少整体到达；
- 协同效果未被评价；
- 修改基础不足；
- 权利要求与说明书不一致。

### 权利要求修改后的处理

修改权利要求后，应针对修改后的完整对象重新执行：

```text
Sem(C')
→ U(C')
→ TA(C')
→ NB
→ 融合路径
→ Δ*
→ IC
```


## 五、新颖性与创造性分析

## 1. 新颖性

新颖性分析应针对完整权利要求对象，而不是只分析某个新增特征。

必要评价单元包括：

```text
U(C)
= CF(C) ∪ REL(C) ∪ CT(C)
```

一张新颖性判断卡原则上只比较：

```text
一项完整权利要求
+
一份合格对比文件
```

不得：

- 跨多份文件补齐新颖性特征；
- 把不同实施例机械拼接；
- 把工程上的合理推断直接当作法律上的必然公开；
- 只比较从属权利要求的附加特征；
- 忽略从属权利要求已经继承的全部上位限定。

## 2. 创造性

创造性分析重点不是“每个特征是否分别找到来源”，而是：

```text
多个独立现有技术网络
能否通过有来源、语义保持且因果闭合的融合路径
整体重构出权利要求技术方案
```

主要模型对象包括：

- `TA`：权利要求目标追溯网络；
- `T_i`：候选文件独立追溯网络；
- `T0(p)`：路径p中的最接近现有技术网络；
- `Tk(p)`：路径p中的补充来源网络；
- `Ω`：允许变换规则集合；
- `FusionOperation`：具体融合操作；
- `TF(p)`：候选融合网络；
- `Δ(p)`：路径p的无来源缺口；
- `Δ*`：不可继续约减的缺口集合族；
- `NB`：新颖性判断卡；
- `IC`：创造性整体评价卡。

创造性模型应检查：

- 来源是否独立；
- 变换是否有来源；
- 变换前提是否成立；
- 结构和功能分配是否保持；
- 接口和行为是否连续；
- 参数约束是否共同可满足；
- `S/B → E` 因果链是否闭合；
- 是否存在申请方案反向补全；
- 是否能够整体到达权利要求方案。

`Δ*`只表示技术事实上的重构缺口，不直接等同于创造性结论。

## 六、使用方式

## 1. 准备输入材料

建议按照以下类别准备材料：

```text
input/
├── 技术交底书
├── 产品结构图或系统框图
├── 流程图、时序图或状态图
├── 实验数据和测试报告
├── 已有专利或技术资料
├── 申请文件草案
├── 审查意见通知书
├── 对比文件
└── 其他法律或程序材料
```

如果材料涉及未公开技术，建议先完成脱敏和权限确认。

不应上传：

- 与撰写无关的客户身份信息；
- 无关商业秘密；
- 不需要处理的个人信息；
- 无法确认来源的第三方材料；
- 超出当前任务范围的内部资料。

## 2. 选择工作模式

### 模式A：申请前技术交底建模

适用于：

- 从技术交底书提炼创新点；
- 建立 R/F/S/B/E 模型；
- 生成检索要素；
- 筛选可保护单元；
- 设计独立权利要求和从属权利要求布局。

示例：

```text
请使用 disclosure 模式分析以下技术交底书：
1. 建立 R/F/S/B/E 模型；
2. 识别核心技术问题；
3. 提取技术特征、关系和技术效果；
4. 输出可检索要素；
5. 区分明确披露、工程推断和待确认内容。
```

### 模式B：已有专利文本建模

适用于：

- 对申请文件进行 MBSE 建模；
- 对比多个专利文件；
- 解析权利要求与说明书；
- 建立权利要求—技术模型映射；
- 分析审查员主张。

示例：

```text
请使用 document 模式处理以下申请文件和对比文件：
1. 建立申请方案的 R/F/S/B/E 模型；
2. 分解权利要求中的 CF/REL/CT/INT；
3. 建立申请文件与对比文件的独立追溯网络；
4. 标记证据来源和待核实内容；
5. 输出差异和可能的法律争点。
```

### 模式C：检索驱动的轻量建模

适用于：

- 已经有简要技术方案；
- 快速生成检索块；
- 展开中英文关键词；
- 形成候选文献检索方向。

示例：

```text
请使用 search 模式，对以下技术方案生成检索块：
1. 提取核心技术对象；
2. 提取功能、结构、行为和效果关键词；
3. 生成中文和英文检索词；
4. 区分核心词、扩展词和排除词；
5. 不直接输出新颖性或创造性结论。
```

## 3. 按阶段确认输出

每个阶段结束后，应检查：

- 输入材料是否完整；
- 技术对象是否明确；
- 关键关系是否遗漏；
- 技术效果是否有依据；
- 待确认内容是否被标记；
- 权利要求是否得到说明书支持；
- 是否存在无来源组合；
- 是否满足当前阶段的输出要求。

确认后再进入下一阶段。

## 八、质量控制原则

### 证据原则

- 原始材料明确记载：`[D]`
- 由明确事实形成的受限工程推断：`[I]`
- 来源缺失、歧义或尚待核实：`[Q]`
- 排除、无关或误混入内容：`[X]`

`[Q]`内容不得直接作为决定性结论的事实基础。

### 权利要求原则

- 独立权利要求应整体反映技术方案；
- 从属权利要求必须继承上位权利要求的全部限定；
- 从权附加特征必须锚定继承网络；
- 多项从属权利要求必须按择一路径分别分析；
- 不得用兄弟从权的限定补足本项从权；
- 不得把说明书中彼此分离的实施方式强行组合。

### 新颖性原则

- 一项权利要求对应一份对比文件；
- 不跨文献补齐新颖性特征；
- 不跨互斥实施例拼接；
- 不以工程推断替代法律上的必然、直接且无歧义公开；
- 从权必须评价继承后的完整技术方案。

### 创造性原则

- 独立建立申请方案网络和现有技术网络；
- 不允许申请方案反向补全现有技术；
- 每个融合操作应具有来源、前提和语义保持条件；
- 不把“可以组合”直接等同于“具有技术启示”；
- 不把 `Δ*` 直接等同于创造性结论；
- 创造性评价始终针对权利要求限定的整体技术方案。

### 治理原则

- 版本、审核、责任和操作记录集中管理；
- 上位权利要求变化时检查全部后代从权；
- 单一从权变化不当然影响兄弟分支；
- AI 可以生成候选对象，但不能自动确认事实；
- AI 操作日志不能替代原始技术证据；
- `draft/reviewed/agreed` 状态必须由适格人员确认；
- 最终法律成果必须由专利代理师审核。

## 九、项目边界

本项目提供的是结构化专利代理辅助方法，不自动推出：

- 专利一定具备新颖性；
- 专利一定具备创造性；
- 专利一定能够获得授权；
- 某项修改一定合法；
- 某项技术一定具有商业价值；
- 某项对比文件一定构成现有技术；
- AI 一定能够提高工作效率；
- MBSE 一定适用于所有案件。

模型输出应当被理解为：

```text
技术事实整理
+
权利要求结构化表达
+
证据定位
+
法律分析辅助
+
审查与复核支持
```

而不是自动化法律裁判。

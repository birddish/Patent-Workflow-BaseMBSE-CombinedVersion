# 权利要求文本审计合同

本文件定义权利要求文本和说明书支持的技术审计，不替代专利代理师的法律判断，也不承担第六章的版本、责任和审批管理。

## 一、ClaimTextAudit接口

```text
ClaimTextAudit {
  claim_id
  path_id
  element_completeness
  relation_condition_check
  dependency_check
  reference_object_name_check
  antecedent_terminology_check
  clarity_scope_check
  support_links[]
  effect_attribution
  modification_delta
  status
  review_note
}
```

`status`只能使用`pass/[Q]/fail/blocked`。状态表示当前技术和文本核验是否完成，不表示授权、侵权、新颖性或创造性结果。

## 二、八项技术审计

1. **要素完整性**：必要对象、模块、步骤、参数和边界是否完整，是否出现孤立名词或遗漏的必要合作关系。
2. **关系与条件**：结构、信号、行为、顺序、触发、状态、参数和约束是否有明确作用对象、方向和语境。
3. **依存关系**：引用编号、在前引用、直接上位项、择一引用、继承限定和增量限定是否兼容。
3A. **从属引用客体名称**：从属权利要求是否完整引用直接上位权利要求所属根主题的客体名称；是否错误地只使用“方法”“设备”“系统”“装置”或“模块”等通用词；多项从属是否逐路径核对。
4. **先行词与术语**：首次出现、后续指代、同义词、缩写、部件名称和功能名称是否稳定且唯一。
5. **清楚性与范围**：相对性术语、范围、阈值、测量条件、功能性表述和负面限定是否可理解、可执行和有边界。
6. **支持关系**：每项权利要求片段是否能定位到说明书段落、附图、结构式、序列表、实验或实施例，并核查特定组合语境。
7. **效果归因**：功能、输出状态和进一步技术效果是否分别记录；效果是否由对应的结构、行为、关系和条件产生。
8. **修改一致性**：修改前后新增、删除或改变的特征、引用边、路径、组合依据和支持位置是否一致，是否超出原始披露范围。

## 三、SupportLink接口

```text
SupportLink {
  claim_span
  description_id
  relation_type
  confidence
  figure_or_assay_anchor
  human_decision
}
```

`relation_type`使用`itself/description/example`。`confidence`仅用于检索候选排序；高置信度不能自动通过支持、清楚性、充分公开或组合依据审计。`human_decision`必须保留人工确认、否定或待核理由。

## 四、AI和自动化边界

推荐顺序为：

```text
已确认技术模型
→ 候选权利要求生成
→ 句法和依赖解析
→ 从属继承/增量审计
→ 支持关系候选检索
→ 清楚性、术语和效果审计
→ 人工确认
```

ROUGE、BERTScore、向量相似度、主题相似度、语言流畅度和模型置信度不得单独使状态从`[Q]`或`draft`升级为`pass`。AI产生的新增技术事实仍需回到原始交底、申请文件或有权技术人员确认。

## 五、阻断条件

- 缺少必要要素、关系、先行词或直接上位引用；
- 从属权利要求缺少完整客体名称，或引用文本与直接上位权利要求的客体名称不一致；
- 多项从属路径被合并，或从属权利要求只评价附加特征；
- 新增限定无继承锚点、无功能作用、无效果路径或无原始支持；
- 支持关系只有相似度分数，没有可定位原文；
- 组合由多个实施例拼接但无CTX/组合依据；
- 修改后引用、路径、术语或支持关系未重算；
- 任何模型分数被直接当作法律结论。

上述条件应分别标记`fail`或`blocked`，并记录回退阶段和待确认问题。

本内容仅为执业辅助参考，最终需专利代理师本人审核确认。

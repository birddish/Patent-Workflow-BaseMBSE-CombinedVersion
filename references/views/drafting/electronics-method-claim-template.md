# 电通方法权利要求输入—功能—输出结构模板

## 一、用途和适用范围

本模板用于阶段3中电子通信、信号处理、网络通信、控制、终端、卫星通信、AI/软件数据处理等技术领域的方法权利要求撰写。

本模板解决的核心问题是：一个电通方法通常由多个步骤组成，每个步骤都应当说明：

```text
输入 I_i → 技术功能 F_i → 输出 O_i
```

每个步骤的基本表述应当能够回答：

> 根据什么输入，执行什么技术功能，生成、确定、更新、发送或输出什么技术结果。

本模板是阶段3的结构模板，不是允许脱离技术交底书自由补写技术内容的句式库。方括号中的内容必须来自阶段1的技术交底、保护单元和已确认来源；无法确认的内容保留 `[Q]`，不得自行补齐。

## 二、核心结构约束

### 2.1 单步骤三元组

每个方法步骤至少具有以下三个要素：

| 要素 | 符号 | 必须回答的问题 | 可接受内容 |
|---|---|---|---|
| 输入 | `I_i` | 根据什么数据、信号、状态、参数或外部事件执行？ | 原始信号、消息、测量数据、状态信息、控制参数、上一阶段输出、网络资源状态 |
| 功能 | `F_i` | 对输入执行了什么技术处理或控制动作？ | 接收、解析、检测、估计、提取、融合、编码、解码、选择、调度、控制、更新、发送 |
| 输出 | `O_i` | 生成、确定、更新、发送或输出了什么技术结果？ | 特征数据、解析结果、估计值、控制参数、调度结果、编码数据、控制指令、更新状态 |

不完整的步骤不得直接进入正式独立权利要求。例如：

```text
仅写“对数据进行处理”——缺少明确功能和输出；
仅写“提高识别精度”——这是效果表述，不是步骤输出；
仅写“采用某模型”——模型名称不能替代输入、处理对象、处理动作和输出。
```

### 2.2 步骤间衔接

对于连续处理链，前一步输出应当成为后一步输入，或者明确说明后一步还接收外部输入：

```text
I_1 → F_1 → O_1
               ↓
       I_2 = O_1 + E_2 → F_2 → O_2
                                      ↓
                              I_3 = O_2 → F_3 → O_3
```

其中：

- `E_i` 表示第 `i` 步独立接收的外部数据、状态或参数；
- `O_i` 如果传递给下一步，应在下一步明确写成输入或处理依据；
- 最终输出应当是可识别的技术数据、技术状态、控制动作或通信结果；
- “提高效率”“增强性能”“实现智能化”等只能作为技术效果，不能单独充当 `O_i`。

### 2.3 独立权利要求的闭合链

独立方法权利要求应形成从输入到技术输出的最小闭合技术链：

```text
外部输入/初始状态
    ↓
S1：I1 → F1 → O1
    ↓
S2：I2（包括O1）→ F2 → O2
    ↓
……
    ↓
Sn：In（包括前序输出）→ Fn → On
    ↓
最终技术结果
```

独立权利要求不要求把说明书中的所有步骤、参数和实现方式全部写入。应当保留能够闭合技术链并体现独立保护价值的必要步骤；具体参数、协议变体、替代算法和可选模块原则上进入从属权利要求分支。

## 三、逐步骤结构模板

### 3.1 工作表模板

在生成权利要求文本前，先为每一个步骤建立下表：

| 步骤 | 输入 `I_i` | 功能 `F_i` | 输出 `O_i` | 下一步使用方式 | 技术交底支持 | 状态 |
|---|---|---|---|---|---|---|
| `S1` | `[输入数据/信号/状态]` | `[具体技术处理动作]` | `[生成/确定/更新的技术结果]` | `O1` 是否作为 `S2` 输入 | `[章节/段落/图号/来源短语]` | `confirmed` / `Q` |
| `S2` | `[O1] + [外部输入]` | `[具体技术处理动作]` | `[生成/确定/更新的技术结果]` | `O2` 是否作为下一步输入 | `[章节/段落/图号/来源短语]` | `confirmed` / `Q` |
| `Sn` | `[前序输出或外部输入]` | `[最终处理或控制动作]` | `[最终技术输出]` | `最终输出用途` | `[章节/段落/图号/来源短语]` | `confirmed` / `Q` |

### 3.2 单步骤句式模板

每一个步骤至少应当能够套入以下结构：

```text
S_i、获取、接收或确定输入[I_i]；
基于所述输入[I_i]执行功能[F_i]，以生成、确定、更新、发送或输出[O_i]。
```

如果输入来自前一步，应改写为：

```text
S_i、基于前一步骤输出的[O_(i-1)]以及[外部输入E_i]，执行功能[F_i]，以生成、确定、更新、发送或输出[O_i]。
```

如果功能包含连续动作，应展开技术动作之间的关系：

```text
S_i、对输入[I_i]执行[F_i1]，得到中间结果[M_i]；
基于所述中间结果[M_i]执行[F_i2]，生成输出[O_i]。
```

不得仅使用下列不可审计的空泛写法：

```text
对数据进行处理；
利用算法得到结果；
根据模型进行判断；
对系统进行优化。
```

除非技术交底同时给出了处理对象、处理动作、处理条件和输出结果，否则上述表述应保持 `conditional` 或标记 `[Q]`。

## 四、独立方法权利要求模板

### 4.1 通用模板

```text
一种由[执行主体]执行的[电子通信/信号处理/控制/数据处理]方法，其特征在于，包括：

S1、获取或接收[输入I1]；
    基于所述输入I1执行[功能F1]，以生成、确定或更新[输出O1]；

S2、基于所述输出O1以及[外部输入E2]执行[功能F2]，以生成、确定或更新[输出O2]；

……

Sn、基于前序步骤输出的[On-1]执行[功能Fn]，以生成、发送或输出[最终技术结果On]。
```

### 4.2 通信或信号处理方法模板

```text
一种[通信/信号处理]方法，其特征在于，包括：

获取[待处理信号、通信消息或信道状态信息]；

基于[处理条件、协议参数或状态参数]对所述[待处理信号、通信消息或信道状态信息]执行[解析、检测、估计、编码、解码、调制、解调或特征提取]，以生成[中间处理结果]；

基于所述中间处理结果执行[选择、配置、调度、控制或信息重构]，以生成[通信参数、控制指令、目标消息或输出信号]；

发送或应用所述[通信参数、控制指令、目标消息或输出信号]。
```

模板中的处理动作只能选用技术交底明确公开的动作。例如，技术交底只公开“分析信号”，不能自行扩展为“滤波、傅里叶变换、特征提取和分类”。

### 4.3 数据处理或 AI 方法模板

```text
一种[数据处理/AI处理]方法，其特征在于，包括：

获取[具有明确技术来源的输入数据]；

对所述输入数据执行[具体的数据预处理、特征构建或数据融合功能]，以生成[中间数据或特征表示]；

基于所述中间数据或特征表示执行[具体推理、估计、分类、检测、预测或控制功能]，以生成[技术判断结果或控制结果]；

根据所述技术判断结果输出[控制参数、设备动作、通信配置、处理结果或更新状态]。
```

模型名称、网络结构名称或算法名称只能作为功能实现方式的一部分，不能替代输入、功能、输出和技术对象。

## 五、从属权利要求模板

### 5.0 从属权利要求的完整客体名称

独立权利要求生成后，先提取其规范化的完整客体名称，作为从属权利要求的引用名称。规范化时通常去掉独立权利要求开头的“一种”，但保留完整的主题限定以及末尾的“方法”“设备”“系统”“装置”或“模块”等客体类型。

从属权利要求不得只使用“方法”“设备”“系统”“装置”或“模块”替代完整客体名称。统一结构为：

根据权利要求[直接上位项编号]所述的[完整客体名称]，其特征在于，……

例如，独立权利要求为“一种基于多源数据融合的工程量估算方法”时，从属权利要求应写成“根据权利要求1所述的基于多源数据融合的工程量估算方法”，不得简化为“根据权利要求1所述的方法”。多项从属必须针对每一条择一路径分别核对完整客体名称；如果不同路径的客体名称不兼容，应阻断生成。
### 5.1 输入限定分支

```text
根据权利要求[直接上位项编号]所述的[完整客体名称]，其特征在于，
所述输入[I_i]包括[具体数据、信号、状态或参数]。
```

### 5.2 功能限定分支

```text
根据权利要求[直接上位项编号]所述的[完整客体名称]，其特征在于，
所述功能[F_i]包括：

对[处理对象]执行[具体技术动作]；
根据[处理条件或判断条件]确定[中间结果]；
基于所述中间结果执行[后续技术动作]。
```

### 5.3 输出限定分支

```text
根据权利要求[直接上位项编号]所述的[完整客体名称]，其特征在于，
所述输出[O_i]包括[具体技术数据、状态、控制参数、消息或控制指令]，
并被用于[下一步骤、目标设备或通信节点]。
```

### 5.4 参数、协议或资源限定分支

```text
根据权利要求[直接上位项编号]所述的[完整客体名称]，其特征在于，
所述功能[F_i]基于[协议、阈值、时间、频率、带宽、资源、状态或参数范围]执行。
```

参数和范围必须有说明书支持；如果缺少测量方法、适用条件、范围来源或基准，应标记为 `[Q]` 或 `conditional`，不得直接写成确定的技术限定。

## 六、方法步骤的结构化数据接口

为了支持阶段3测试和后续文本审计，每个步骤可以结构化为以下对象：

```json
{
  "step_id": "S1",
  "reference_target_claim_id": "C1",
  "reference_object_name": "[独立根主题的完整客体名称]",
  "reference_text": "根据权利要求1所述的[完整客体名称]，其特征在于……",
  "reference_name_match": true,
  "input": {
    "items": ["[输入数据、信号、状态或参数]"],
    "source": "[外部输入/前序输出/说明书来源]",
    "condition": "[适用条件；无则填写 null]"
  },
  "function": {
    "action": "[具体技术处理动作]",
    "object": "[被处理对象]",
    "mechanism": "[已确认的处理机制；未知则保留 [Q]]"
  },
  "output": {
    "items": ["[生成、确定、更新、发送或输出的技术结果]"],
    "type": "data|state|parameter|control|message|signal|other",
    "used_by": ["S2"]
  },
  "source_phrase_spans": ["[技术交底中的来源短语]"],
  "support_links": ["[章节/段落/图号/来源标识]"],
  "certainty": "confirmed|Q|conditional"
}
```

该对象是阶段3的结构化中间表示，不等于最终权利要求文本。最终文本仍需经过权利要求类型、依赖关系、支持关系和文本审计。

## 七、硬门和状态规则

### 7.1 步骤完整性

下列任一情形存在时，该步骤不能直接标记为 `pass`：

- 缺少输入，无法确定处理对象或处理依据；
- 缺少技术功能，只剩下结果或效果描述；
- 缺少输出，无法确定该步骤产生的技术结果；
- 输出与下一步骤没有关系，也没有说明其最终技术用途；
- 功能由模型名、算法名或模块名代替，但没有具体技术动作；
- 关键输入、功能或输出不是技术交底中的已确认内容。

### 7.2 输出状态

```text
confirmed：输入、功能、输出和来源均已确认；
candidate：结构完整，但仍需与金标准或人工文本审查比较；
conditional：结构基本完整，但存在待确认的输入、功能、输出或支持关系；
blocked：缺少核心输入、功能或输出，不能形成闭合技术链；
[Q]：具体技术事实尚未确认，不得被写成确定性特征。
```

### 7.3 不得补写的内容

除非技术交底、夹具或已授权来源明确支持，不得擅自补写：

- 未公开的通信协议、网络拓扑或设备角色；
- 未公开的算法步骤、模型层结构或训练方式；
- 未公开的阈值、范围、时间、频率、带宽或资源预算；
- 未公开的硬件模块、传感器、处理器或存储器关系；
- 仅从“效果”倒推出的输入、功能或中间结果。

### 7.4 从属引用客体名称硬门

下列任一情形存在时，从属权利要求不得标记为 pass：

- 缺少 reference_object_name；
- reference_object_name 不是直接上位权利要求所属根主题的完整客体名称；
- reference_text 只使用“方法”“设备”“系统”“装置”或“模块”等通用词；
- 引用文本中的客体名称与 reference_object_name 不一致；
- 多项从属的某一条 DepPath 没有单独完成名称核对。

此类缺口应保持 conditional、fail 或 blocked，不得生成正式提交候选版。
## 八、阶段3使用顺序

电通方法权利要求应按以下顺序处理：

```text
1. 确认执行主体和方法根主题；
2. 列出全部候选步骤；
3. 为每个步骤补齐 I_i、F_i、O_i；
4. 检查 O_i → I_(i+1) 的衔接；
5. 选择能够闭合技术链的必要步骤形成独立项；
6. 将参数、协议、替代方式和可选模块分配到从属分支；
7. 为每个权利要求建立来源短语和支持链接；
8. 生成候选文本并执行 ClaimTextAudit；
9. 对缺口保留 candidate、conditional、[Q] 或 blocked，不得伪造为 pass。
```

在受控 `stage1_stage3_claim_core` 模式下，技术交底书直接作为阶段1输入，阶段2保持 `mocked_pass`；本模板只服务于阶段3的权利要求核心撰写，不触发检索、查新截止日判断、答审或复审结论。

## 九、最终检查清单

```text
[ ] 每个独立权利要求步骤都有输入；
[ ] 每个独立权利要求步骤都有具体技术功能；
[ ] 每个独立权利要求步骤都有技术输出；
[ ] 前一步输出已连接到后一步输入，或已说明外部输入来源；
[ ] 最终输出不是单纯的抽象效果；
[ ] 执行主体、技术对象和方法边界明确；
[ ] 没有用模型名称、算法名称或模块名称替代具体功能；
[ ] 每项从属权利要求均有明确依赖路径；
[ ] 每项从属权利要求均引用完整客体名称，而非仅使用方法、设备、系统或装置等通用词；
[ ] 每个输入、功能和输出均有来源或支持链接；
[ ] 未确认内容保留为 [Q]、conditional 或 blocked；
[ ] 生成结果仍需与权利要求金标准进行比较，金标准不作为无依据补写来源。
```

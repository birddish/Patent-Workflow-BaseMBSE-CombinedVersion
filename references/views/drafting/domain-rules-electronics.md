# 电子通信/AI/软件域撰写规则

## 规则状态与文件边界

本文件已对齐标准撰写技能的通用接口，适用于电子通信、AI、软件、算法、信号处理、网络、控制、天线、卫星及结构化数据案件。本文供阶段 1 至阶段 5、阶段 8 和阶段 9 使用。

本文只规定电子通信/AI/软件技术对象的建模、权利要求撰写、说明书支持和文本审计。`DepPath`、`Sem_eff`、`DependentClaimTrace`、`ClaimTextAudit`、`SupportLink` 等对象的通用定义以对应合同文件为准；本文不建立第二套权利要求树。

版本、责任、审批、影响集和生命周期由第六章及通用治理接口处理。协议版本、软件版本或数据格式版本在本文中仅作为技术特征，不能与治理层版本对象混同。`pass/[Q]/fail/blocked` 只表示技术或文本核验状态，不表示授权、侵权或创造性法律结论。

## 一、电子通信/AI/软件技术对象

### 1.1 特征单元

| 单元 | 至少记录的内容 | 撰写和审计重点 |
|---|---|---|
| 硬件模块 | 处理器、存储器、传感器、天线、收发器、芯片、加速器 | 连接、能力、执行条件和资源是否明确 |
| 软件/算法模块 | 检测器、估计器、解析器、校验器、生成器、融合器、控制器 | 输入、步骤、状态、输出和实现约束是否完整 |
| 数据项 | 采样值、信道状态、数据包、特征向量、参数集 | 类型、格式、单位、维度、精度、语义和来源 |
| 信号/协议 | 信号格式、帧结构、调制、协议、API、总线 | 字段、版本、状态、时序、同步和错误处理 |
| 处理步骤 | 接收、解析、检测、估计、融合、选择、输出 | 前置状态、后置状态、执行主体和顺序 |
| 技术参数 | 频率、功率、增益、时延、带宽、码率、误码率 | 测量方法、工况、范围、资源预算和基线 |
| 技术对象 | 终端、基站、网络节点、天线、芯片、机器人或工程模型 | 算法或软件是否对具体技术对象施加约束或控制 |

算法、模型或模块名称不能代替输入、行为、技术对象和效果。仅从附图或通用常识推断的内容保持 `[I]` 或 `[Q]`。

### 1.2 电子通信域 R/F/S/B/E 最小链

```text
R 技术问题和技术约束
→ F 输入/处理/输出或控制功能
→ S 硬件、软件、数据、协议和接口实体
→ B 算法步骤、信号流、状态转换、时序和资源行为
→ E 受影响技术对象和可观察技术指标
```

权利要求应体现：具体技术输入、与技术数据关联的处理、算法/软件与技术对象的功能性交互、技术输出或受控技术对象，以及客观技术效果。

## 二、独立权利要求撰写规则

### 2.1 方法和系统权利要求

- 优先采用“技术输入→解析/检测/估计→融合/选择/校验→结构化结果或控制输出”的完整链条；
- 上游结果对发明必要时，应记载达到该结果所需的最少生成过程；
- 系统独立权利要求与对应方法的必要功能保持同构，不自动汇总全部方法从属特征；
- 模块名称、API、类名或模型品牌应转换为体现技术含义的模块、单元、信息、步骤或处理关系；
- 不把抽象数学模型、商业规则、展示规则或通用信息处理本身作为技术贡献；
- 只有在算法处理具体技术数据、约束技术对象或改善可观察技术指标时，才作为具有技术作用的特征。

### 2.2 数据和协议表述

- 数据项应说明类型、格式、维度、单位、来源和处理状态；
- 协议、帧、API、总线和信令应说明字段、状态、顺序、同步、寻址和错误处理；
- 技术参数应说明测量方法、工况、范围、资源预算和比较基线；
- 估算、补全或待校正数据不得表述为已经直接获取的确定性事实；
- 不以“提高智能化”“体验更好”“效率更高”等无客观指标的表达替代技术效果。

### 2.3 交底覆盖

在形成不限项母版后，将已披露技术模块分别归入：

- 独立权利要求必要特征；
- 从属权利要求回退特征；
- 其他保护主题；
- 仅实施例的实现细节；
- 不纳入或待确认的特征及理由。

彼此平行的编辑、渲染、局部修复、BIM、工程导出或控制分支不得为压缩项数而强行合并。

### 2.2 电通方法步骤的输入—功能—输出结构

电通方法权利要求的每个步骤应按以下结构建模：

```text
输入 I_i → 技术功能 F_i → 输出 O_i
```

即：根据输入数据、信号、状态或参数，执行明确的技术处理或控制功能，生成、确定、更新、发送或输出可识别的技术结果。O_i 应当成为下一步骤的输入或处理依据，除非该输出已经是最终技术结果。

阶段3具体使用模板见 `references/electronics-method-claim-template.md`。该模板要求先建立逐步骤工作表，再生成独立权利要求和从属分支：

```text
S1：I1 → F1 → O1
S2：I2（包括 O1 或明确的外部输入）→ F2 → O2
……
Sn：In（包括前序输出）→ Fn → On
```

每个步骤缺少输入、功能或输出时，不得直接生成正式候选项；缺少技术交底支持的内容必须保留 `[Q]`，并将整体状态保持为 `conditional` 或 `blocked`。模型名称、算法名称、模块名称和抽象技术效果不能替代具体输入、技术动作和输出。

## 三、从属权利要求和 MBSE 映射

### 3.1 完整从属对象

从属权利要求先沿每一条合法 `DepPath` 展开全部继承的数据、步骤、模块、协议、参数和技术对象约束，再识别本项 `DeltaSem`。有效对象是完整 `Sem_eff`，不能只评价新增算法步骤、参数或数据项。

新增限定至少归入以下一类：

- 数据语义、格式、维度或来源细化；
- 协议字段、信令顺序、同步或错误处理收缩；
- 算法步骤、中间状态或路径选择细化；
- 硬件资源、执行环境、并发、时延或参数阈值限定；
- 与继承技术对象形成输入—处理—输出或控制协同的限定。

每项新增限定必须具有继承锚点、技术作用或效果路径，并通过 `DependentClaimTrace` 记录。

### 3.2 分支和多项从属

- 线性从属逐级累计全部数据流、处理步骤、硬件约束和输出限定；
- 兄弟分支只继承共同上位网络，一个分支的算法、协议或参数不得进入另一个分支；
- 多项从属按每一个择一引用路径分别生成 `DepPath`、`Sem_eff` 和审计结果；
- 不得把多个上位权利要求的输入、步骤、模块或参数取并集；
- 参数、数据或协议细化使用 `refine` 连接继承节点，不删除或替换继承节点；
- 已并入独立权利要求的技术输入、算法步骤或硬件约束，不得再次作为从权的独立贡献。

## 四、说明书支持和客观效果

通过 `SupportLink` 将输入数据、处理步骤、模块、协议、参数、中间状态、输出和效果定位到说明书、附图、实施例、代码/伪代码或测试材料。至少核对：

- 输入是否具有具体技术含义；
- 算法或软件是否与技术对象发生功能性交互；
- 中间状态、数据格式、协议字段和执行顺序是否完整；
- 硬件资源、时延、带宽、功耗或并发条件是否有依据；
- 技术输出是否为可观察的技术结果或对技术对象的控制；
- 效果是否具有客观指标、比较基线、适用工况和范围覆盖。

通过 `EffectEvidenceCard` 记录效果来源、比较基准、来源日期、适用条件和权利要求覆盖。仅有模型预测、文本相似度或单一测试结果时，标记 `[Q]`，不得直接形成确定效果结论。

## 五、电子通信/AI/软件域 ClaimTextAudit

调用通用 `ClaimTextAudit` 和 `SupportLink`，至少检查：

| 审计项目 | 电子通信/AI/软件域问题 |
|---|---|
| 输入完整性 | 输入数据、信号、协议或技术对象是否具体明确 |
| 数据语义 | 类型、格式、单位、维度、来源和状态是否一致 |
| 处理链闭合 | 解析、检测、估计、融合、选择、校验和输出步骤是否连贯 |
| 技术交互 | 算法/软件是否约束或控制具体技术对象 |
| 协议/时序 | 字段、版本、状态、同步、寻址、错误处理和顺序是否明确 |
| 资源/参数 | 硬件、存储、算力、带宽、时延、功耗和测量方法是否支持 |
| 从属完整性 | 是否继承全部上位限定，是否存在路径合并或分支泄漏 |
| 术语转换 | API、类名、模型名和实现术语是否转成技术性权利要求语言 |
| 支持关系 | 说明书、附图、实施例或测试材料是否可定位 |
| 效果归因 | 效果是否归属于当前技术特征组合并有客观指标 |
| 修改一致性 | 修改后输入、处理、输出、依存关系和支持是否一致 |

审计状态只使用 `pass`、`[Q]`、`fail`、`blocked`。自动评分、模型置信度和向量相似度不能单独升级审计状态。

## 六、电子通信/AI/软件域阻断条件

出现以下任一情形，至少标记 `[Q]`，必要时标记 `blocked`：

- 从属权利要求没有展开完整继承方案；
- 多项从属路径被合并或兄弟分支发生泄漏；
- 新增数据、算法、协议、硬件或参数没有继承锚点；
- 权利要求只有抽象算法、商业规则或结果标签，没有具体技术对象；
- 输入、处理、中间状态和技术输出不能形成连续链；
- 协议、接口、时序、同步或错误处理条件不明确；
- 估算、补全或待校正数据被写成直接获取事实；
- 技术效果没有客观指标、比较基线、适用工况或原始支持；
- 仅凭模型相似度、自动评分或通用常识认定技术贡献；
- 实施主体、硬件执行条件或资源约束缺少支持。

## 七、域特定待确认门

以下事项保留为 `[Q]`，逐案核实后再更新规则：

| 编号 | 待确认事项 | 影响阶段 | 通过条件 |
|---|---|---|---|
| E-Q01 | 抽象算法与技术性贡献的边界 | 阶段 3 | 算法处理具体技术数据并作用于技术对象或指标 |
| E-Q02 | 协议/API/总线版本和兼容条件 | 阶段 3/5 | 字段、状态、时序、同步和错误处理能够定位 |
| E-Q03 | 多设备或多模块协作的技术对象边界 | 阶段 3 | 输入、执行主体、控制关系和输出责任可识别 |
| E-Q04 | 技术效果的可测性和比较基线 | 阶段 3/5 | 指标、工况、测量方法和范围覆盖明确 |
| E-Q05 | AI 模型训练/推理特征的必要性 | 阶段 3 | 模型步骤、输入、输出和技术交互有原始支持 |
| E-Q06 | 电子通信域 MBSE 视图的选择和适配 | 阶段 1 | 数据流、信号流、状态和资源视图语义一致 |

## 八、受控回归的电子根主题分支

电子通信/AI/软件案件必须先区分执行主体、模块层级和技术输出，再生成权利要求树：

- 控制方法、信号处理方法、数据处理方法属于 method 根主题；控制节点、处理器、接收器、终端或设备属于 device/module 根主题；多节点协同及其连接关系属于 system 根主题。
- “第二控制节点执行的方法”“第一控制节点执行的方法”等不同执行主体和状态链不得合并为一个方法根主题；控制节点装置、处理器/接收器装置和系统根主题也不得因共享数据流而合并。
- 方法与对应装置/系统可以保持必要功能同构，但只在说明书分别给出对象边界和闭合技术链时登记平行根主题；方法从权不得被改写成装置独权，装置分支不得静默并入系统根主题。
- 每个根主题和分支必须记录 object_type、object_label、实施主体、source_phrase_spans、branch_relation 和 candidate_claim_ref。

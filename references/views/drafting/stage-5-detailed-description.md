## 输出目标与文件边界

生成可直接粘贴进中国专利申请文件“具体实施方式”部分的正文。正文与内部审校材料必须分开：

- **申请文件正文**：只写术语说明、实施例、具体实施方案、对实施方案的必要扩展说明以及技术效果。
- **内部审校附件**：写权利要求映射、技术交底证据、追溯链、MBSE节点、证据状态、待确认问题和质量检查结果。
- 不得把“MBSE”“追溯链”“需求节点”“功能节点”“物理节点”“行为节点”、节点编号、权利要求映射表、证据状态、`[Q]`、阶段确认单或执业辅助提示写进申请文件正文。
- 在交付消息或独立审校附件中给出执业辅助提示、待确认问题和阶段确认单，不得污染可直接使用的正文文件。

## 前置与输入

核验已确认的阶段1至阶段4版本及阶段3锁定的权利要求Markdown母本。以阶段3权利要求书确定说明书必须覆盖的技术方案，以技术交底书和经发明人或有权技术人员确认的补充技术事实确定具体实现，以阶段1内部追溯结果校验技术效果，并读取`node-claim-mapping.md`的四层映射账本和效果证据记录。涉及AI、软件、算法或数据结构时，同时读取`domain-rules-electronics.md`。

若缺少已确认的实现依据，不得用常识、推测或未经确认的模型输出补写具体参数、处理机制、性能指标或因果关系。将缺口记入内部审校附件；在正式正文中删除无依据的细节，或仅采用已有材料能够支持的上位表达。

对权利要求中承担技术作用的术语，至少披露其输入、处理、输出和适用的异常处理。下列内容一旦写入权利要求、作为技术效果依据或作为使方案可实施的必要机制，即触发充分公开审校：硬约束与软约束的映射、差分约束或等效求解条件、候选方案的生成/去重/停止条件、评分降级或置信度处理、锁定冲突处理以及无解反馈。未获项目证据支持时，不得虚构数值、优先级、阈值、模型参数或性能数据；应采用有依据的功能性或可选性表述，或者在内部记录中标为不采用。

## 正文整体形式

参照成熟“具体实施方式”文件采用下列顺序，不输出写作分析或中间推理：

1. `# 具体实施方式`；
2. 必要时写便于理解方案的引导语；
3. 集中解释首次出现且影响方案理解的关键术语；
4. 以独立权利要求形成一个完整主实施例，并按技术主题归组设置优选实施方式、系统实施方式或可选实施方式；
5. 每个完整实施例严格按“权利要求整体—说明及扩展整体—技术效果整体”的三块顺序连续撰写；
6. 全部实施例后，根据需要设置`## 本发明所取得的技术效果`，归纳主技术链产生的整体技术效果。

不得在正文中出现“以下为权利要求转写”“扩展内容”“对应权利要求X”“来源于技术交底书”“内部追溯结果”等撰写过程用语。

## 每个实施例的强制三块结构

采用“一个完整主实施例＋按技术点归组的优选实施方式”为默认结构。每项已确认权利要求的技术特征均须在正文中可定位，系统、装置、电子设备、存储介质或程序产品权利要求也应获得与其主题相适配的实施例支持；但不得为每项从属权利要求机械复写整套主流程。

以独立权利要求形成主实施例；以技术主题对从属权利要求的新增或细化特征进行归组。需要完整呈现引用后技术方案的优选实施方式保留“三块”结构；仅对主实施例作局部限定、且不改变主流程或技术效果链的从属特征，可在同一优选实施方式中逐项定位说明。不得把从属权利要求的新增特征仅附会为无对应关系的一句补充说明。

每个实施例的申请文件正文只能采用以下顺序：

`第一块：权利要求整体 → 第二块：说明及扩展整体 → 第三块：技术效果整体`

三块之间不得交错。在第一块最后一个权利要求步骤、模块或技术特征写完之前，不得插入任何具体实现、字段解释、参数举例、应用场景或扩展段落；第二块开始后，不得返回补写尚未转入的权利要求步骤；第三块只能在第二块全部完成后开始。任何“一个权利要求步骤—该步骤的说明及扩展—下一个权利要求步骤”的结构均为不合格结构，必须重写整个实施例。

### 第一块：权利要求整体

- 忠实覆盖该权利要求的全部技术特征，不得遗漏、改变引用关系或把必要特征降格为可选特征。将权利要求中的每一项步骤、模块、数据限定、条件、分支和“所述”引用逐项核对；任何一项未在第一块定位即判为不合格，不得移入第二块补救。
- 删除“根据权利要求X所述”“其特征在于”等权利要求格式用语。以“本实施例提供……，包括：”起始，连续写完该权利要求对应的全部步骤、模块或技术特征。
- 独立权利要求按其完整技术链连续表达。对从属权利要求，将其引用的基础方案与新增或细化限定合并为引用后的完整技术方案；除非用户明确允许简写，不得用“S1至S6执行实施例1所述处理”等概括性援引代替权利要求整体。
- 对从属实施例，独立权利要求已有步骤的编号、名称、处理对象和技术含义必须保持一致；新增内容属于对既有步骤的输入、条件、处理结果、存储、保留或复用的限定时，将其并入被限定的既有步骤或该步骤的子步骤，不得挤占、改名、后移或重编号基础步骤。仅当新增内容具有独立处理谓词且不能归入任何既有步骤时，方可新增步骤，且不得改变基础步骤的相对顺序。
- 第一块只做说明书化转写，不解释某一步骤如何具体实现，不举例，不写字段、参数、接口、替代方式或技术效果。

#### 权利要求层级解析与子步骤替代

- 转写前逐级解析方法权利要求的句法层级。遇到“包括：”“包含：”“具体包括：”“通过以下步骤”等引导语，且其后列出两个以上具有独立处理动作的分号分隔项、换行项或并列项时，将引导语之前的操作识别为上位操作，将每个并列处理动作识别为用于替代该上位操作的独立子步骤。
- 方法方案使用`S1`、`S2`等主步骤，使用`Sx-1`、`Sx-2`等表示`Sx`的子步骤；只有权利要求本身还存在下一层列举时，才继续使用`Sx-1-1`等编号。对于在`Sx`执行前实施的预处理、校验或准备动作，可使用`Sx-0-1`等编号。
- 当一个上位操作通过“包括：”“包含：”“具体包括：”“通过以下步骤”等引导语列出两个以上独立处理动作时，必须在第一块中用`Sx-1`、`Sx-2`等子步骤序列直接替代`Sx`，不得另行保留或输出`Sx：……，包括：`这一父步骤。各子步骤分别承载权利要求记载的具体动作及对应结果，并共同实现该上位操作；不得因多个动作共同形成同一上位结果而把它们合并为一个步骤。
- 将上位操作中对各子步骤共同适用的输入、前提、条件或结果关系准确写入相关子步骤，确保省略`Sx`行后不丢失权利要求限定。不得通过新增一个无编号总括句变相保留父步骤，也不得擅自扩大或缩小共同限定的适用范围。
- 以“是否具有独立的处理谓词及处理对象或结果”判断是否拆分，不以逗号数量或名词数量判断。同一处理动作产生多个并列输出时仍为一个子步骤；紧随该动作的结果归属、数据命名或用途限定与该动作保持在同一子步骤，除非权利要求将其记载为另一独立处理动作。
- 保持权利要求记载的先后、并行、条件和引用关系。子步骤编号表示结构层级，不当然表示权利要求未记载的执行时序；不得为凑编号而增加、删除、调换或推断处理动作。
- 例如，权利要求记载“多模态解析包括语义解析、几何检测和深度估计”时，应写成：

```markdown
S2-1：对增强草图图像进行建筑语义解析，得到相应建筑语义信息；  
S2-2：对增强草图图像进行几何检测，得到相应几何信息；  
S2-3：对增强草图图像进行深度估计，得到相应深度信息，并将权利要求指定的信息作为空间层次解析结果。  
```

  不得在上述子步骤之前另写`S2：对增强草图图像进行多模态解析，包括：`，也不得写成单一`S2`后接三个无编号的处理动作。示例仅演示替代关系和编号，实际术语、输入及输出必须忠实采用已确认权利要求。
- 不得令同一编号对应不同处理，不得出现步骤自我引用。系统或装置方案必须完整转写权利要求列举的模块、单元、连接关系和功能协同，不得因其不属于方法步骤而省略技术特征。
- 权利要求本身含有判断分支时，在第一块内连续写明总判断步骤、进入条件和全部分支步骤；在总步骤后紧邻定义各分支，不得仅写“进入Sx-x”后在远处说明该步骤。分支写完后再结束第一块。
- 不得在申请文件正文或附图源中使用“执行实施例X所述步骤”“执行实施例X所述的S1至Sn”等引用占位语替代应当写出的完整技术方案。

### 第二块：说明及扩展整体

仅在第一块完整结束后，以“在本实施例中”“具体地”或同类申请文件用语开始第二块。按照第一块的步骤、模块或技术特征顺序，对完整方案进行集中说明和扩展。可以使用“对于S1……”“对于S2-1……”等表述建立对应关系，但所有说明和扩展必须整体位于全部权利要求内容之后。

根据已披露内容说明：

- 输入及其来源、输出及其去向；
- 数据对象、必要字段及字段的技术含义；
- 模块或步骤之间的数据传递、调用关系和执行次序；
- 判断条件、分支选择、阈值用途、校验、回退和异常处理；
- 关键处理的可执行过程、接口、脚本或设备协同方式；
- 能够帮助实施该方案的应用场景、替代实现或优选方式。

对技术交底书中可识别的实现机制逐项覆盖，包括但不限于字段及其技术含义、服务或模块协作、结构化数据解析、JSON清洗重试、校验规则、异常处理、回退生成、脚本、接口、渲染或工程导出。对每一机制记录其被写入的实施例段落；未写入时，记录其仅作为可选实施方式、已进入权利要求或经确认省略的理由。不得仅以“可进行清洗重试”概括交底书已披露的具体处理链。

扩展的目的仅是具体说明权利要求方案如何实施以及为何能够产生相应技术作用，不得借扩展擅自增加新的发明构思，不得把未披露的模型结构、算法参数、训练数据、实验结果或性能指标写成事实，也不得让实施例与权利要求形成相互矛盾的保护范围。

第二块内部依照第一块已经确定的主步骤及替代子步骤顺序分段扩展。第一块已用`Sx-1`、`Sx-2`等子步骤替代`Sx`时，第二块必须分别对应这些子步骤说明，不得重新补写或合并为一个`Sx`；不得在第二块首次创建本应位于第一块的权利要求子步骤，也不得把第一块遗漏的权利要求特征伪装成扩展内容补入第二块。发现遗漏或层级错误时，返回第一块重新生成整个实施例。第二块不得逐步骤插入独立的技术效果结论。

从第一块进入第二块、从总步骤进入子步骤、从步骤说明进入数据或模块说明时，使用“在本实施例中”“为了实现上述步骤”“具体地”“基于此”等过渡语句，使叙述对象、前提和承接关系清楚。不得在一个完整段落后孤立出现子步骤、字段清单或实现细节。

### 第三块：技术效果整体

仅在第二块的全部说明和扩展完成后，统一撰写该实施例的技术效果。不得在第一块或第二块中穿插分步骤技术效果，也不得在技术效果开始后返回补写具体实施方案。

按以下因果顺序组织一个或多个连续段落，但不得把箭头、链编号或审校字段带入正文：

`本实施例的技术特征/关系 → 行为及输出状态 → 受影响对象及属性 → 客观技术效果E → 解决或缓解的技术问题`

技术效果必须由本实施例整体方案中实际写明的S/B/REL/CV及其输出状态因果地产生，并在内部效果证据记录中对应受影响对象、受影响属性、技术后果、适用条件和证据状态。`F.Output`或`STATE.OutputState`只是直接输出，不得换词复制为E；E仅写“实现了某功能”、没有受影响属性或脱离具体因果路径仍被宣称成立时，应删除或回退核实。避免只写“提高效率”“提升智能化”“方便使用”“改善体验”等空泛结论；没有实验或计算依据时，不写具体提升比例或无法验证的比较结论。绝对E不强制比较，比较型E必须说明比较基线、差异方向和适用范围。

## 全部实施例后的本发明技术效果

在所有实施例之后，以如下固定引导语和编号形式归纳整体技术效果：

`本发明通过上述实施例，取得了如下技术效果：`

`1、……；`

`2、……；`

每一项均应对应至少一个已写明的技术特征或协同关系，并按“技术特征/关系—行为及输出状态—受影响属性—技术效果—技术问题”组织；不得把实施例中没有记载的效果、参数或比较结论写入该总结。

### 正文结构模板

```markdown
## 实施例N

本实施例提供……，包括：
S1：……；
S2-1：……；  
S2-2：……；
……
Sn：……。

在本实施例中，对上述步骤的具体实施方案说明如下。对于S1，……；对于S2-1，……；对于S2-2，……；……；对于Sn，……。

本实施例通过……，使……，从而……。
```

模板中的第一块必须先连续列完全部主步骤及替代子步骤，之后才能开始说明及扩展；通过上述引导语列出两个以上独立处理动作的`Sx`不得再单独出现。模板中的三个块级标题仅用于内部理解，不写入申请文件正文。

## 内部追溯校验（正文之外）

为每个实施例在独立审校附件中建立追溯记录，至少包括：

`实施例编号 → 对应权利要求及技术特征 → 正文段落或步骤 → 具体实现证据及位置 → 扩展说明 → B及OutputState → 受影响对象/属性 → 技术效果E → 所解决或缓解的技术问题 → 证据状态/待确认事项`

同时建立以下三项审校表：

1. **权利要求转实施例逐项核对表**：权利要求号、技术特征原文、上位操作与子步骤层级、被替代的上位步骤编号、替代子步骤编号、实施例第一块位置、`所述`引用关系、核对结果；
2. **技术交底实现机制覆盖表**：交底书位置、实现机制、实施例位置、处理方式（权利要求/实施例/可选流程/省略）、理由；
3. **可选流程保护决策表**：可选流程、是否具备独立技术意义、增加从属权利要求/保留为明确可选实施例/删除、决定理由；
4. **步骤/模块主表（亦为权利要求步骤基准表）**：步骤或模块ID、对应节点组及关系组、输入、输出、条件/分支、权利要求特征组、说明书段落、附图节点、基础步骤编号/名称/处理对象/技术含义、允许并入的限定、对应从属实施例位置及核对结论。该表是方法步骤、系统模块和最终DOCX编号的唯一基准；
5. **主创新点叙事覆盖表**：主创新点要素、CHAIN/PU/PST/CTX、实施例位置、系统实施例位置、整体技术效果位置、事实来源轴、撰写采用轴及缺口处理结论。
6. **充分公开触发审校表**：触发机制、对应权利要求/术语、输入、处理、输出、异常边界、交底或确认依据、正文位置及审校结论。
7. **技术效果证据记录**：效果ID、技术特征/协同关系、B及OutputState、受影响对象、受影响属性、技术后果、适用条件、因果路径、效果类型、比较基线（如适用）、证据位置/状态及正文位置。

已有MBSE节点或链编号时，只将其记入该内部记录，用于检查“技术问题—技术方案—技术效果”是否闭环。正文仅保留由追溯结果验证后的自然语言技术内容，严禁出现MBSE名称、图名、节点类型、节点编号或“追溯链条”等内部分析表达。

## 主创新点与步骤基准校验

主实施例与从属实施例均以步骤/模块主表为准。基础步骤的编号、名称、处理对象和技术含义不得变化；存储、保留、复用、输入补充、条件或处理结果等限定，必须并入其所限定的基础步骤或该步骤的子步骤。不得凭空设置S0或以新增步骤挤占基础步骤。拒绝条件、脱敏处理和内容返回必须分别定位到权利要求对应的判断、处理和返回步骤。阶段5交付的说明书母本必须回填该表中的实际段落和步骤位置；最终DOCX仅可据此表复核编号和模块名称。

主创新点的每个因果要素均须在主实施例、适用的系统实施例及“本发明所取得的技术效果”中可定位。涉及行为记录、基线更新或后续风险判断的方案，应说明记录输入、更新对象、后续调用关系和产生的技术作用，不得只罗列日志模块、风险模块和决策模块。

扩展内容仅在内部审校附件中分开登记`fact_status`和`drafting_status`：N只由发明人或有权技术人员确认，G必须回指D/N，X不得进入正文。上述状态、主创新点编号及审校表不得写入申请文件正文。

## 术语与表达规则

- 在术语首次出现或首次承担关键技术作用时给出可理解的技术解释，不以字段释义代替操作过程。
- 对灭点、地平线、完整度、有效闭合底面、处理优先级等不属于一般日常语言且参与判断、分支、校验或回退的术语，在其首次产生技术作用处说明“含义—输入数据—判断或计算规则—触发条件—对后续处理的作用”。实现细节术语如JSON清洗、data URL或脚本标记仅在其首次实际使用的步骤中说明，不应脱离实施过程集中堆砌。
- 代码字段、API、类名、服务名、模型名或脚本名只有在其有实现意义且来源材料已披露时才可出现；同时说明其技术含义，避免以商业产品名限定方案。
- 保持权利要求、实施例和附图中的对象名称、步骤编号、模块名称及引用关系一致。MBSE名称只参与内部一致性校验，不作为正文术语。
- 使用申请文件语体，不写“建议”“可能需要补充”“据交底书可知”“经检索发现”等审校或论证语言。

## 交付物

1. **主文件：具体实施方式Markdown**。仅包含可直接进入申请文件的正文。
2. **独立内部审校附件**。逐实施例列明权利要求覆盖、具体实现证据、扩展依据、追溯链、技术效果因果链、缺失证据和待确认事项。
3. **阶段确认单**。登记阶段5输入版本、正文版本、审校附件版本、待确认问题、前序依赖和下一阶段；置于正文文件之外。

当用户仅要求“可直接粘贴的具体实施方式”时，优先交付主文件；审校附件和确认单分文件或在交付说明中另附，不得与主文件合并。

## 质量检查与确认门

- 逐条检查权利要求全部技术特征是否进入对应实施例，并检查从属新增限定是否处于正确步骤、模块或数据关系中。
- 使用步骤/模块主表逐项核验主、从属实施例：不得凭空出现S0，基础步骤不得改名、重编号、后移或改变处理对象；存储、保留、复用等限定必须并入被限定步骤或其子步骤；每个步骤或模块必须能回指对应节点组、关系组、权利要求特征组和说明书段落。
- 分别核验拒绝条件、脱敏处理和内容返回的步骤归属；任何判断条件误写为处理步骤、处理动作误写为返回步骤或反向错位，均要求重写相应实施例第一块。
- 使用主创新点叙事覆盖表检查主实施例、系统实施例和整体技术效果；主创新点任一必要因果要素无可定位披露时，不得标记阶段5完成。
- 逐项扫描权利要求中的“包括：”“包含：”“具体包括：”“通过以下步骤”等层级引导语。其后存在两个以上独立处理动作时，检查第一块是否已用数量相符、逐项对应的`Sx-1`、`Sx-2`等子步骤直接替代上位步骤；仍保留`Sx：……，包括：`父步骤，或者出现单一`Sx`后接两个以上无编号处理动作时，直接判定不合格并重写该实施例。
- 检查拆分依据是独立处理动作而不是输出名词数量：不得漏拆语义解析、几何检测、深度估计等并列动作，也不得把单一动作产生的多个并列输出错误拆成多个步骤。
- 使用权利要求转实施例逐项核对表，逐项确认步骤、模块、条件、分支、数据限定及“所述”引用已进入第一块；任何遗漏、错位、降格或拆散均要求整体重写相应实施例。
- 逐实施例定位三个边界：第一块最后一个权利要求步骤、第二块首段及末段、第三块首段；确认全部权利要求内容均位于全部说明及扩展之前，全部说明及扩展均位于技术效果之前。
- 出现“权利要求步骤—说明或扩展—后续权利要求步骤”的任何交错，直接判定该实施例不合格并整体重写，不得仅移动单个段落补救。
- 对需要完整呈现引用后技术方案的从属实施例，检查其是否呈现完整方案；对归入同一优选实施方式的局部限定，检查其与主实施例和对应权利要求均可定位。未经用户允许使用“S1至S6执行实施例1所述处理”等概括性援引时，判定不合格。
- 逐实施例检查是否同时具有权利要求整体、说明及扩展整体、技术效果整体以及独立内部追溯记录；缺一项不得标记完成。
- 检查每项扩展均有技术交底书或经确认补充材料的依据，每项效果均能由正文技术特征和技术效果证据记录支持；不得以无机理、无作用对象或无适用条件的笼统效果代替因果论证。
- 检查技术交底实现机制覆盖表和可选流程保护决策表已经闭合；不得使具有独立技术意义的已披露流程在无明确决定的情况下既未进入权利要求、又未被标为可选实施例或删除。
- 检查主文件不存在MBSE、追溯链编号、证据标签、`[Q]`、待确认事项、映射表、阶段确认单或执业辅助提示。
- 检查主步骤、替代子步骤及更深层步骤的编号连续且含义唯一，子步骤层级与权利要求的列举层级一致，通过上述引导语拆分的`Sx`未作为父步骤另行输出，第二块逐项对应第一块的子步骤，`Sx-0-y`仅用于`Sx`执行前的动作，分支定义紧邻，术语和引用关系一致，方法与系统对应；检查全文在需要分行处使用硬换行而非空白段落。
- 登记阶段5版本及所依据的阶段3权利要求Markdown版本。阶段3题名、术语、编号、逻辑顺序、特征取舍、必要关系或主创新点组合变化时，具体实施方式自动标为待复核。只有专利代理师明确确认具体实施方式正文、内部审校附件、步骤/模块主表、技术效果证据记录、充分公开触发审校及与权利要求Markdown母本的一致性后，方可进入阶段8；阶段6、阶段7仅在用户明确启动时另行适用。

## 阶段 8 配套：锁定权利要求补强模式

用户锁定权利要求时，本阶段固定输出为“插入位置 + 可直接粘贴正文 + 内部依据说明”。除非用户另行授权，不改写权利要求或原 DOCX。

对于质量评分、完整度、优先级、路径选择、回退、参数补全等判断性术语，正文必须明确含义、输入、处理规则、触发条件、输出状态、异常边界和对后续步骤的作用。N类正文还须覆盖待解决技术问题、处理机制、冲突处理、人工校正入口和技术效果，并在内部依据说明中登记发明人或有权技术人员的确认情况。

允许采用“主实施例 + 成组优选实施方式”，避免为每项从属权利要求机械复写整套主流程；内部权利要求—说明书映射仍须逐项可定位。

# 阶段五：答复审计

## 目的

对阶段四完成的审查意见答复或复审意见陈述书进行系统、独立的审计，确保论证质量、事实准确性和格式规范，避免将存在缺陷的文书提交至专利局。

## 审计维度

### 零、答审链条双向闭包审计

先建立并逐项核对以下两条方向：

```text
正向：审查意见 → OAIssue → 证据段落 → 区别/效果
      → CombinationPath/断点 → ResponseEvent/AmendmentEvent → DecisionTrail
反向：审查结果 → 结果理由 → ResponseEvent/AmendmentEvent
      → 具体争点 → CombinationPath → 对比文件及证据段落
```

任一方向无法走通，答复只能标记为 `content_status=conditional`，不得表述为内容完全通过。审计还必须确认结果理由没有反向替代中间技术事实。

### 一、事实一致性审计

逐项核验答复中的事实陈述是否与阶段二的事实核实报告一致。

| 检查项 | 审计方法 | 审计结论 |
|--------|---------|---------|
| 引用审查员观点的准确性 | 与阶段二的审查员原文逐字比对 | ✅ / ⚠️ / ❌ |
| 引用对比文件内容的准确性 | 与阶段二的原文定位比对，确认无遗漏限定或过度概括 | ✅ / ⚠️ / ❌ |
| 引用本申请内容的准确性 | 与本申请原文比对 | ✅ / ⚠️ / ❌ |
| 未使用阶段二标记为"不支持"的事实作为肯定性陈述 | 逐一比对 | ✅ / ❌ |
| 未遗漏审查意见中的任何问题 | 与审查意见原文逐项比对 | ✅ / ❌ |

**常见错误**：
- 在答复中引用审查员观点时擅自改写，导致原意偏移；
- 将阶段二中"部分支持"的事实当作"完全支持"使用；
- 跳过了审查意见中的某个次要问题。

### 二、论证逻辑审计

核验创造性论证的逻辑链条是否完整，是否有阶段三的分析支撑。

| 检查项 | 审计方法 | 审计结论 |
|--------|---------|---------|
| 区别特征分组是否符合技术路线 | 与阶段一的模型比对 | ✅ / ⚠️ / ❌ |
| 区别特征分组是否有断裂（将一体化的特征拆散） | 检查各组特征之间的技术配合关系是否被割裂 | ✅ / ⚠️ / ❌ |
| 每个非显而易见性论证是否有追溯链分析支撑 | 与阶段三的断裂点/冲突节点比对 | ✅ / ⚠️ / ❌ |
| "结合不可能"结论是否有接口兼容性分析支撑 | 与阶段三的接口兼容性分析表比对 | ✅ / ⚠️ / ❌ |
| 技术启示反驳是否完整（不遗漏审查员的任何启示主张） | 与阶段三的技术启示判断表逐项比对 | ✅ / ❌ |
| 是否存在循环论证（以结论为前提） | 检查论证中是否用"A具备创造性"来证明"A具备创造性" | ✅ / ❌ |
| 是否存在跳跃论证（缺少中间推理步骤） | 检查每个结论是否有完整的推理链条 | ✅ / ⚠️ / ❌ |
| 是否先核实最接近现有技术、区别特征和实际技术问题 | 与 IS 卡及审查意见原文逐项比对 | ✅ / ⚠️ / ❌ |
| 每项组合反驳是否有启示、动机、兼容性或成功预期的证据 | 与 EV/IS 和阶段三分析比对 | ✅ / ⚠️ / ❌ |

**常见错误**：
- 将阶段三中"部分成立（需适配）"的技术启示当作"完全不成立"处理；
- 区别特征分组割裂了一体化的技术配合关系；
- 用"本领域技术人员不会想到"替代具体的技术障碍分析。

### 三、权利要求版本审计

| 检查项 | 审计方法 | 审计结论 |
|--------|---------|---------|
| 引用的权利要求文本为用户最新版本 | 与用户提供的最新文本比对 | ✅ / ❌ |
| 无旧版权利要求措辞残留 | 全文搜索旧版特征措辞 | ✅ / ❌ |
| 每项修改在原申请文件中均有支持依据 | 逐项检查支持依据的段落/权利要求编号 | ✅ / ❌ |
| 修改说明中的引用段落编号正确 | 逐项核验原文 | ✅ / ⚠️ / ❌ |
| 已纳入独立权利要求的特征未在从属权利要求部分重复论证 | 检查从属权利要求部分 | ✅ / ❌ |
| 活动权利要求集合、快照和主策略各自唯一 | 核对 `active_claim_set_id`、`active_snapshot_id`、`primary_strategy_id` | ✅ / ❌ |
| 修改影响闭包中的NB/IS路径覆盖率均为100% | 核对 `recalculation_gate` 预期与完成集合 | ✅ / ❌ |
| 旧NB/IS和旧答复追溯已失效 | 检查所有非活动快照记录的生命周期状态 | ✅ / ❌ |

### 四、措辞审慎性审计

| 检查项 | 审计方法 | 审计结论 |
|--------|---------|---------|
| 无无支持的效果断言（"显著提高""大幅改善"等） | 搜索效果断言关键词 | ✅ / ⚠️ / ❌ |
| 无将未要求保护的参数转化为明示限定 | 检查"大""小""高""低""长""短"等词的使用语境 | ✅ / ⚠️ / ❌ |
| 尺寸相关表述使用审慎措辞 | 检查是否有"提供……结构基础""适于……""能够……"等限定语 | ✅ / ⚠️ / ❌ |
| MBSE 符号（R1/F1/S1/B1/E1 等）已全部转换为技术语言 | 全文搜索 MBSE 符号 | ✅ / ❌ |
| 无过度热情的客套用语（除非用户要求） | 检查开头和结尾 | ✅ / ⚠️ |
| 无夸大无支持的"必然""一定""只能"等绝对化表述 | 搜索绝对化措辞 | ✅ / ⚠️ / ❌ |

### 五、格式与引用审计

| 检查项 | 审计方法 | 审计结论 |
|--------|---------|---------|
| 申请号、申请人、发明名称正确 | 与申请文件比对 | ✅ / ❌ |
| 对比文件编号（D1/D2）全文一致 | 全文检查 | ✅ / ❌ |
| 段落引用编号正确 | 随机抽检 20% 的引用 | ✅ / ⚠️ / ❌ |
| 权利要求编号与最新文本一致 | 与最新权利要求文本比对 | ✅ / ❌ |
| Markdown 层级结构正确 | 检查标题层级 | ✅ / ⚠️ |
| 关键内容已直接呈现 | 检查每个实质问题、权利要求特征、对比文件主张、修改支持和效果主张是否有原文或直接内容，而非只有编号/路径/文件名 | ✅ / ⚠️ / ❌ |
| 不存在 citation-only 段落 | 检查是否出现只有编号、页码、段落号、路径或文件名而没有直接原文的实质段落 | ✅ / ❌ |

### 六、证据链可追溯性审计

| 检查项 | 审计方法 | 审计结论 |
|--------|---------|---------|
| 论证中的关键事实陈述可反向追溯到阶段二的核实结论编号 | 逐条追溯 | ✅ / ❌ |
| 论证中的技术启示反驳可反向追溯到阶段三的断裂点/冲突节点编号 | 逐条追溯 | ✅ / ❌ |
| 论证中不存在无法追溯至前序阶段的"凭空"论断 | 标记无溯源的论断 | ✅ / ❌ |

### 七、问题覆盖与保护范围审计

| 检查项 | 审计方法 | 审计结论 |
|---|---|---|
| 每个审查意见问题有唯一主处理动作 | 对照问题—处理动作矩阵 | ✅ / ❌ |
| 问题、证据、答复位置与结论可双向追溯 | 逐行检查 `response_trace` | ✅ / ⚠️ / ❌ |
| 每项修改都记录保护范围变化 | 对照修改事件 | ✅ / ❌ |
| 需要申请人选择的范围取舍已明确标记 | 检查客户确认项 | ✅ / ❌ |

### 八、答复模式与效果证据审计

| 检查项 | 审计方法 | 审计结论 |
|---|---|---|
| `ArgumentOnly` 未误写为补正后效果 | 核对 `response_mode`、ClaimVersion 和修改事件 | ✅ / ❌ |
| `AmendmentBased` 已完成旧分析失效与新模型重建 | 核对 `supersedes`、影响闭包、TA/NB/IS 重算和重算门 | ✅ / ❌ |
| 每项技术效果均有 `EffectEvidenceCard` | 检查来源、比较基准、日期和权利要求范围覆盖 | ✅ / ⚠️ / ❌ |
| 新增实验未冒充申请日公开事实 | 检查证据日期和措辞 | ✅ / ❌ |

### 九、内容正确性与提交就绪性分离审计

分别评定以下两个状态，不得合并为单一的“通过”：

| 状态 | 可选值 | 含义 |
|---|---|---|
| `content_status` | pass / conditional / fail | 技术事实、权利要求、论证和追溯关系的正确性 |
| `submission_status` | ready / blocked | 提交期限、形式信息、客户确认、签章/替换页等是否齐备 |

如任一核心事实、对比文件资格或修改支持依据为 `Q`，`content_status` 不得为 `pass`。如申请人范围取舍、提交期限或形式信息未确认，`submission_status` 必须为 `blocked`。

### 十、五方一致性与决定性Q传播审计

| 检查项 | 审计方法 | 审计结论 |
|---|---|---|
| 活动集合、问题注册表、NB/IS、答复段落和就绪状态引用同一快照 | 从 `active_snapshot_id` 双向追溯 | ✅ / ❌ |
| OA问题、问题注册表和活动答复追溯一一对应 | 比较稳定问题指纹和 `response_trace` | ✅ / ❌ |
| 文献资格Q未形成确定NB/IS风险或结论 | 检查资格轴与 `conclusion_status/risk` | ✅ / ❌ |
| 覆盖特征Q未形成完整覆盖或明确不覆盖 | 检查全部活动NB | ✅ / ❌ |
| 启示、动机、兼容性或成功预期Q未使组合路径闭合 | 检查全部活动IS | ✅ / ❌ |
| 修改支持Q未成为主策略 | 检查 `amendment_strategies` | ✅ / ❌ |

## 审计结论处理

| 结论 | 处理方式 |
|------|---------|
| ✅ 通过 | 无需处理 |
| ⚠️ 需修正 | 在答复中直接修正，修正后重新审计该单项 |
| ❌ 严重问题 | 回退至对应阶段（阶段一/二/三/四）修正后重新流转 |

## 最终交付确认

- [ ] 审计报告已完成，所有审计维度均已覆盖；
- [ ] ❌ 类问题已回退修正并重新审计通过；
- [ ] ⚠️ 类问题已修正并复核；
- [ ] 最终版答复文本与审计报告一并交付。
- [ ] 问题覆盖率为 100%，无未处理的 `office_action_issue`；
- [ ] 对外答复稿不含内部 ID、状态标签或 MBSE 术语；
- [ ] `content_status` 与 `submission_status` 已分别给出，且阻塞项和客户确认项已列明。
- [ ] 正向和反向答审链条均已闭包至 `DecisionTrail`，结果理由可回写到具体证据段落；
- [ ] `ArgumentOnly`/`AmendmentBased` 模式与权利要求版本、效果证据卡和重算门一致。
- [ ] 每个实质论证点均遵循“原文摘录 → 来源定位 → 对应关系 → 分析 → 申请人回应”，不存在只给引用编号而不呈现内容的段落。

**仅在所有 ❌ 类问题关闭后，方可交付最终答复文本；仅在 `submission_status=ready` 时，方可表述为“可提交”。**

## 补充：来源—用途审计

终审增加一项来源性质审计：检查每个论文、预印本、数据集、官方材料和演示是否按其 `source_status/research_role` 使用；检查自动评分、语义相似度和候选生成是否被误写为原始支持、法律证据或答复成功率；检查 A1 等官方实践材料未被列为同行评议论文。来源性质缺失时，应降低结论强度或标记 `Q`，而不是自行补齐资料性质。

### 审计门的可执行判定

阶段五应输出一张机器可核对的审计表：

| 审计门 | 通过条件 | 失败处理 |
|---|---|---|
| 问题登记 | 审查意见问题数与 `OAIssue` 一一对应，每项仅一个主处理动作 | 回退阶段二 |
| 证据回指 | 每个答复段落、区别特征和效果均可回指原文位置或明确 `Q` | 保持条件性 |
| 版本重算 | 每次补正都有新 `ClaimVersion`，影响闭包覆盖100%，旧分析失效 | 回退阶段零/三 |
| 双向闭包 | `DecisionTrail` 可正向到达结果并反向回到证据 | `submission_status=blocked` |
| 模式隔离 | `ArgumentOnly` 不改变权利要求集合；`AmendmentBased` 已重算 | 拒绝定稿 |
| 对外稿清洁 | 不含内部ID、节点符号、状态标签、模型评分或任务标签 | 仅保留内部工作稿 |

活动快照使用 `freeze_revision`；旧 `frozen_hash` 仅可作为历史字段读取，不参与新任务校验。`content_status` 与 `submission_status` 必须分别报告，存在决定性 `Q`、缺失来源位置或闭包断点时不得标记 `ready`。

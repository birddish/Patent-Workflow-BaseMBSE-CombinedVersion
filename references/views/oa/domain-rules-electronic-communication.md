# 电子通信/AI/软件域撰写规则（审查意见答复）

## 规则说明

本文件是 electronic-communication mode 的域规则，供阶段一至五按需读取。它把电子通信、AI、软件案件的技术事实组织成可重放的 R/F/S/B/E 链，并将域特定断点交给 domain-argument-patterns-electronic-communication.md。域规则不把模式命中、FusionFeasible 或自动评分直接转换为法律结论。

## S 节点分类与证据要求

| S 节点类型 | 典型内容 | 必须补充的域事实 |
|---|---|---|
| 硬件模块 | 处理器、存储器、传感器、天线、收发器、芯片、加速器 | 型号/能力、连接、资源和执行条件 |
| 软件/算法模块 | 检测器、估计器、解析器、校验器、生成器、融合器、控制器 | 输入、步骤、状态、输出和实现约束 |
| 数据项 | 采样值、信道状态、数据包、特征向量、参数集 | 类型、格式、单位、维度、精度、语义和来源 |
| 信号/协议 | 信号格式、帧结构、调制、协议、API、总线 | 版本、字段、状态、时序、同步和错误处理 |
| 处理步骤 | 接收、解析、检测、估计、融合、选择、输出 | 前置状态、后置状态、执行主体和顺序 |
| 技术参数 | 频率、功率、增益、时延、带宽、码率、误码率 | 测量方法、工况、范围、资源预算和比较基线 |

每个关键节点和关系必须标注来源位置及 D/I/Q/X 状态。算法、模型或模块名称不能代替输入、行为、技术对象和效果；仅从附图或通用常识推断的内容应保持 I 或 Q。

## R/F/S/B/E 建模规则

- R：记录技术问题、应用环境和约束，不以领域标签代替问题。
- F：记录输入、处理、输出或控制功能，并写明数据语义和功能性交互。
- S：记录硬件、软件、数据、协议和接口实体。
- B：将方法步骤、信号流、状态转换、时序、资源调度和控制行为串联起来。
- E：记录受影响技术对象、客观指标、工况、比较基准、测量方法和因果来源；泛化的“提高效率/准确率”只能标为 Q，直到有可核验基线。

新颖性核实关注单一文件是否覆盖完整节点和关系；创造性分析必须另行建立 CombinationPath，检查多源路径能否保持接口、行为、约束和 S/B→E 因果。

## 域论证模式路由

阶段三和阶段四按以下选择器读取域模式文件：

| pattern_id | 何时使用 | 关键字段 |
|---|---|---|
| EC-01 | 跨文件输出—输入接口、类型或语义不连续 | 数据类型、格式、维度、精度、转换和语义保持 |
| EC-02 | 协议、API、总线、架构、信令或同步不连续 | 版本、字段、状态、时钟、寻址、错误处理 |
| EC-03 | 算法与硬件、资源、并发或实时性不能共同满足 | 算力、存储、传感器、带宽、功耗、截止时间 |
| EC-04 | 内部处理链缺少 Dk 所需中间状态 | 步骤、前置处理、中间结果、状态生命周期 |
| EC-05 | 问题、对象、约束和教导方向不匹配 | 实际问题、数据、目的、选择方向、成功预期 |
| EC-06 | 技术性边界或算法—技术对象耦合争点 | 技术输入、控制对象、客观指标、S/B→E 因果 |

模式可并用，但每个命中都必须关联 OAIssue、CombinationPath、TeachingRecord 和 EffectEvidenceCard。EC-05 不得只凭“领域不同”命中；EC-06 通过技术性检查后仍需回到创造性组合分析。

## 电子通信与信号处理字段块

按案件实际情况记录：

- 信号类型、采样率、量化、编码、调制和信道状态；
- 帧结构、协议版本、信令、同步、时钟、寻址和错误处理；
- 天线、RF/baseband、阵列、传感器、处理器和加速器依赖；
- 时延、吞吐、误码率、功耗、带宽、内存和并发预算；
- 输入—处理—输出的语义保持，以及输出如何作用于技术对象。

## AI/机器学习字段块

必须区分训练、推理和在线更新：

- 数据来源、标签/特征、维度、预处理、训练/推理阶段；
- 模型结构、参数更新、推理硬件和资源约束；
- 模型输出如何进入信号、设备、网络、控制或存储操作；
- 指标、工况、比较基线和范围覆盖；
- 不把训练数据量、模型名称或通用准确率单独写成技术效果。

## 软件与控制字段块

- API/服务边界、数据库/缓存/I/O、消息队列和协议；
- 状态、事件、并发、锁、调度、资源隔离和失败恢复；
- 被控制的设备、信号、存储或网络对象；
- 方法步骤的执行主体及系统权利要求的单一主体可实施性；
- 软件结构名称、伪代码或类名须转换成可核验的技术行为。

## 答复措辞与证据卡

### 技术事实、工程推断、法律评价三层分开

- 技术事实：文件明确公开的节点、关系、步骤、参数和效果证据。
- 工程推断：在前提明确且可复核时的接口、资源、时序或性能推断，标为 I。
- 法律评价：结合动机、技术启示、显而易见性等下游判断，不能反写成 MBSE 事实。

“工程上可以另行设计”与“现有技术给出了到达路径”必须分别陈述。任何“不兼容”段落都应先重放 D0、Dk 及操作序列，再说明断点。

### EffectEvidenceCard 最低字段

effect_id、受影响技术对象、客观指标、比较基准、工况/样本、测量方法、支持段落、申请日可得性、权利要求范围覆盖、D/I/Q 状态。

没有比较基准、工况或范围覆盖时，效果只可作为待核验或有限支持，不能作为确定性意外效果。

### TeachingRecord 最低字段

teaching_id、D0/Dk、所解决问题、目的、选择方向、明确教导、必要适配、阻碍因素、合理成功预期、证据段落和 Q 项。

## ArgumentOnly 与 AmendmentBased

- ArgumentOnly：保持当前 ClaimVersion，回答事实错误、区别、效果、结合动机、阻碍因素或融合断点。E-01 Tanaka 的意见书样本只能作为该模式的经验分类。
- AmendmentBased：新建 AmendmentEvent 和 ClaimVersion，核验修改支持，重新生成 TA、NB、CombinationPath、Δ*、EffectEvidenceCard 和 ResponseTrace；旧结论标记失效或待重算。
- 任何补正候选均需通过原始支持、范围影响、活动集合冻结和 recalculation_gate；候选模型或相似度不得直接生成对外文本。

## 电子通信域常见误区

- 不把“特征分别出现在 D1、D2”写成“自然形成同一系统”；
- 不把“不同协议/领域/格式”写成无需具体断点的绝对不兼容；
- 不以“升级硬件即可”掩盖未经来源支持的关键适配；
- 不在没有资源、时序或接口证据时断言算法“无法运行”；
- 不把通用数学算法、商业规则、信息展示或模型名称直接当作技术贡献；
- 不以单一技术效果或引用数量证明创造性；
- 不把 FusionFeasible=false、模式命中或模型评分直接写成法律结论；
- 不在对外稿暴露 pattern_id、OAIssue、CombinationPath、D/I/Q/X 等内部标识。

## 领域特定答复句式（须填事实）

- EC-01：D0 输出【Y】，Dk 输入要求【X】；案卷未显示保持【语义/精度/维度】的转换步骤，故组合路径的输入适配尚待证明。
- EC-02：D0 的【协议/架构】依赖【字段/状态/时钟】，Dk 依赖【另一机制】；需具体重连和同步步骤，不能仅以协议名称差异作结论。
- EC-03：Dk 需要【硬件/资源/截止时间】，D0 提供【条件】；在未找到【适配来源】前，相关约束的共同可满足性仍为待核验工程事实。
- EC-04：Dk 步骤以【中间状态】为输入，D0 链路未产生或未保留该状态；应指出缺失的前置步骤及其时延、误差和资源影响。
- EC-05：D0 的实际问题/数据/约束为【X】，Dk 的教导方向为【Y】；领域差异只有在与问题、接口、约束和成功预期共同形成断点时才具有论证意义。
- EC-06：输入为【技术数据】，处理直接作用于【技术对象】，在【工况】下影响【客观指标】；技术性判断与创造性组合判断分开完成。

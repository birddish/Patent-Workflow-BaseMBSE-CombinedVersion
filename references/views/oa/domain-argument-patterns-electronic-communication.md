# 电子通信/AI/软件域论证模式

## 使用边界与答审链条

本文件供 electronic-communication mode 在阶段三“追溯链与技术启示分析”和阶段四答复撰写时按需读取。六类模式是选择器，不是固定结论；只有当案卷事实能够定位到具体节点、关系、行为、参数或效果时才使用。技术领域不同、技术名称不同或工程上可以改造，均不能单独推出“不能组合”或“具备创造性”。

电子通信/AI/软件案件统一沿以下链条工作：

~~~text
审查员主张
  → 引证证据段落/附图
  → 权利要求特征的 R/F/S/B/E 节点
  → 区别特征与技术效果
  → CombinationPath（D0、Dk、操作、Ω、中间状态）
  → 数据/协议/硬件/时序/资源/效果闭合检查
  → ResponseEvent 或 AmendmentEvent
  → ClaimVersion 与重新评价
  → DecisionTrail 及结果理由
~~~

本域的正向技术链通常表示为：

~~~text
技术输入数据
  → 受约束的算法/软件处理
  → 技术输出或对技术对象的控制
  → 可观测技术指标
  → EffectEvidenceCard
~~~

“技术性/客体资格”是进入实体创造性分析前的边界检查；创造性实体分析关注多源路径能否保持同一技术方案的语义、接口、行为、约束和效果因果。Could-Would 仅在已有技术事实和 CombinationPath 后作为下游规范接口，不能生成追溯链、证明接口兼容或替代效果证据。

## 模式选择矩阵

| pattern_id | 主要断点 | 首要 MBSE 对象 | 不得单独推出 |
|---|---|---|---|
| EC-01 | 跨文件数据接口、类型或语义不连续 | F/S/B：输入输出、格式、维度、语义 | 仅因数据格式不同即必然不能组合 |
| EC-02 | 协议、接口、架构或同步条件不连续 | S/B：帧、信令、API、总线、状态和时钟 | 仅因协议名称不同即没有技术启示 |
| EC-03 | 算法与硬件、资源或实时性约束不共同可满足 | S/B：处理器、存储、传感器、资源预算、时限 | 未核实硬件约束就断言“算法无法运行” |
| EC-04 | 同一内部处理链缺少必需中间状态 | F/B：步骤顺序、中间结果、状态转换 | 把跨模块输入转换问题重复归入本模式 |
| EC-05 | 技术问题、数据对象、约束和教导方向不匹配 | R/F/B/E：问题—手段—效果和 TeachingRecord | 仅凭技术领域标签差异否定动机 |
| EC-06 | 算法与技术对象的耦合不足，或技术性边界被混淆 | R/F/S/B/E：输入—处理—控制—效果 | 仅凭“使用计算机”或“使用 AI”确认技术贡献 |

## 所有模式共用的 CombinationPath 记录

每条路径至少记录下列字段；缺字段时将对应结论降为 Q 或条件性意见：

| 字段 | 记录要求 |
|---|---|
| path_id、claim_version_id | 绑定当前权利要求版本和唯一争点 |
| D0、Dk 及证据段落 | 写明最接近文件、补充文件及其承担的技术作用 |
| feature_transfer | 被提取的节点、关系、行为或参数 |
| operation_sequence | 加入、替换、关系重连、行为重排及每一步中间状态 |
| Ω | 允许的适配、转换或参数调整；必须有来源或明确工程前提 |
| interface_constraints | 数据、协议、硬件、资源、时序、环境和执行主体 |
| positive_closure | 来源、节点语义、接口、行为、共同约束及 S/B→E 因果是否闭合 |
| reverse_break | 节点身份、接口转换、功能分配、时序/状态、效果归属和问题是否断裂 |
| TeachingRecord | 技术问题、目的、选择方向、明确/隐含教导、阻碍因素和合理成功预期 |
| EffectEvidenceCard | 效果对象、比较基准、条件、测量方法、范围覆盖和来源日期 |
| response_action | ArgumentOnly、AmendmentBased、补充核验、客户确认或其他行动 |

### 正向闭合与反向断裂

只有同时满足以下条件，才能把路径标记为工程上的 FusionFeasible；该状态不是法律结论：

~~~text
来源闭合
∧ 节点语义保持
∧ 接口连续
∧ 行为/时序连续
∧ 资源和参数约束共同可满足
∧ S/B → E 因果闭合
~~~

任一条件失败时，必须指出失败发生在哪个中间状态，而不是只写“D1 与 D2 不兼容”。“工程上可另行设计”与“依据现有技术能够到达”分开记录。

### 答复模式与版本门

- ArgumentOnly：权利要求和 ClaimVersion 不变，回应事实、区别、效果、动机、阻碍因素或路径断点。不能写成补正后的授权结果。
- AmendmentBased：新建 AmendmentEvent 和 ClaimVersion，记录支持位置及范围影响，重新生成 TA、NB、CombinationPath、Δ* 和效果卡；旧分析标记 superseded/invalidated，未通过 recalculation_gate 不得形成对外稿。
- 对外答复不得出现 pattern_id、CombinationPath、EffectEvidenceCard、D/I/Q/X 等内部符号；内部 ResponseEvent 和 DecisionTrail 仍需保留完整链接。

## EC-01 数据接口与数据语义断裂

### 适用与边界

用于 D0 的正常输出与 Dk 模块输入之间的跨文件接口断点，须具体说明类型、格式、维度、精度、采样、编码或技术语义。若缺口只是同一处理链内部没有产生中间状态，使用 EC-04；若核心是协议栈、帧或时钟，优先使用 EC-02。

### 需要核实的事实

- D0 输出节点及其产生步骤，是否为系统正常工作路径；
- Dk 输入节点的类型、单位、维度、精度、采样率、编码和语义；
- 是否存在明确的转换、解码、归一化、重采样或语义映射；
- 转换是否保持后续算法所需的信息和技术效果。

### CombinationPath 与 Ω

记录 D0 输出 → 转换/适配 → Dk 输入的每一步。Ω 只能包括文件明确教导、共同标准直接给出或已核实的必要适配；不得把未说明的转换器、训练数据或语义标注作为无记录的桥接。

### 正向闭合

若 D0 已公开转换节点，Dk 明确接受该转换后的数据，且转换保持维度、精度、语义和后续效果，路径可继续；此时不得使用 EC-01 作绝对阻断。

### 反向断裂

重点检查：是否需要新增无来源转换；模拟/数字、二维/三维、时域/频域、软判决/硬比特等语义是否改变；转换后是否仍能支持 Dk 的行为和效果。

### 证据与答复动作

EffectEvidenceCard 应绑定转换前后数据的技术指标及比较基准。TeachingRecord 应记录 Dk 是否给出该转换方向、目的和成功预期。可采取争辩、补充核验或在确有支持时补正；禁止仅凭“格式不同”直接写“具备创造性”。

### 可对外改写模板

> 审查员主张将 Dk 的处理模块接入 D0 的输出。经核对，D0 在其正常工作路径中输出的是【Y】（证据位置），而 Dk 的输入前提是具有【X 属性】的【X】（证据位置）。现有路径未记录从【Y】到【X】的转换及其对【语义/精度/维度】的保持方式。因而，审查员所复述的组合尚缺少一个可重放的输入适配步骤；该技术事实需要与技术启示和合理成功预期一并评价。

## EC-02 协议、接口、架构与同步不兼容

### 适用与边界

用于协议栈、帧结构、信令、API、总线、集中式/分布式架构、版本、寻址、状态机或时间同步条件造成的路径断点。协议名称不同本身不够，必须说明改变了哪一接口、状态或行为。

### 需要核实的事实

- D0 与 Dk 的协议版本、帧字段、信令顺序、寻址、认证、API/总线和架构假设；
- 两者的时钟、同步、时延、并发、可靠性和错误处理条件；
- 是否存在明确适配层、网关、协议转换、兼容模式或共同标准；
- 适配是否会改变 D0 的工作原理、功能分配或效果。

### CombinationPath 与 Ω

将“替换模块”“加入适配层”“重连接口”“重排信令”分开记录，写明适配前后的状态和新增依赖。若必须改变底层协议或核心架构，不得将其压缩为简单模块替换。

### 正向闭合与反向断裂

正向闭合要求字段、状态、时钟、寻址和错误处理共同可满足，并且 Dk 的行为在 D0 架构中仍保持。反向断裂包括字段不存在、信令顺序冲突、集中/分布式功能分配冲突、同步预算不满足或适配导致原有技术效果失去归属。

### 证据与答复动作

TeachingRecord 应比较两文件要解决的问题、选择协议的方向和适配成本；EffectEvidenceCard 应记录吞吐、误码率、时延、同步误差或功耗等客观指标。仅“LTE 与 Wi-Fi 不同”不足以完成论证，必须落到帧/信令/接口/同步的可核验断点。

> D0 采用【协议/架构 A】，关键字段和状态转换为【具体内容】；Dk 的教导依赖【协议/架构 B】中的【字段/机制】。将 Dk 接入 D0 需执行【适配/重连/重排】并同时满足【同步/时延/资源】约束。案卷未显示该操作的来源、方向和成功预期，因此目前只能认定组合路径存在具体技术断点，不能仅凭协议名称差异作出法律结论。

## EC-03 算法、硬件、资源与实时性不匹配

### 适用与边界

用于算法、模型或软件行为依赖处理器类型、GPU/NPU/FPGA、存储、传感器/天线、操作系统、带宽、功耗、并发或截止时间，而 D0 与 Dk 的约束不能共同满足。没有来源或测试支撑时，不得断言“无法运行”。

### 需要核实的事实

- Dk 算法的明确硬件、内存、算力、带宽、传感器、并行度和时限要求；
- D0 的实际硬件、系统、资源预算和运行状态；
- 约束是文件明确记载、技术上受限推断，还是待确认 Q；
- 是否有降阶、量化、分片、调度、加速器或替代实现的明确教导。

### CombinationPath 与 Ω

分别记录硬件替换、资源重分配、调度改变、模型压缩和算法改写；不得把“升级设备”作为不受限的 Ω。若改变硬件架构才可实现，必须说明该修改是否仍是审查员所主张的路径。

### 正向闭合与反向断裂

正向闭合要求计算量、存储、带宽、功耗和截止时间在同一环境下共同可满足，且核心算法行为及效果仍保持。反向断裂包括缺少必要传感器/阵列、资源预算冲突、实时截止时间超限、并发状态不一致或替代实现改变了输出指标。

### 证据与答复动作

EffectEvidenceCard 记录延迟、吞吐、能耗、内存占用、误码率或推理精度的比较基准。TeachingRecord 应说明 Dk 是否教导在 D0 约束下运行或如何克服约束。可争辩或补充核验；只有权利要求和原文有明确支持时才补正。

> Dk 的【算法/模型】明确依赖【硬件/资源/时限】；D0 仅提供【实际条件】。在当前 CombinationPath 中，尚未找到来源支持的【替换/调度/压缩】步骤，且【指标】约束不能共同满足。因此应先把“无法运行”降格为有条件工程判断，再分析是否存在技术启示和合理成功预期。

## EC-04 信号/数据处理链的中间状态缺失

### 适用与边界

用于同一系统或内部处理链中，Dk 的步骤以某一中间状态为输入，而 D0 的连续步骤并不产生该状态。它与 EC-01 的区别是：EC-04 关注处理链内部状态和时序，EC-01 关注跨模块/跨文件的输入输出接口。

### 需要核实的事实

- D0 的完整步骤、状态、输入和输出；
- Dk 所需中间结果的定义、产生条件和生命周期；
- D0 是否已在其他步骤隐含生成该结果，及其证据强度；
- 插入前置处理是否改变时延、误差、资源或技术效果。

### CombinationPath 与 Ω

记录“插入前处理 → 生成中间状态 → 执行 Dk 步骤”的中间状态。Ω 不得无来源地增加信道估计、特征提取、ROI、解调解码或其他关键状态。

### 正向闭合与反向断裂

正向闭合要求中间状态可由既有步骤连续产生、状态条件满足且误差/时延预算仍闭合。反向断裂包括需要新增关键前处理、软判决与硬比特混用、状态生命周期不一致或插入步骤抵消原有技术效果。

### 证据与答复动作

EffectEvidenceCard 记录中间状态对最终指标的贡献及对照条件。TeachingRecord 记录 Dk 是否教导该前处理和嵌入方向。答复应先重放 D0 步骤，再指出缺失的状态生成步骤，不得只写“无法无缝接入”。

> Dk 的【步骤 X】以【中间状态 M】为输入；D0 的实际链路为【步骤序列】，其中未产生或未保留 M。审查员路径因此还缺少【前置处理/状态转换】这一具体操作，并需重新核验其时延、误差和资源影响。

## EC-05 技术领域、问题与技术教导不匹配

### 适用与边界

用于比较 D0 与 Dk 的技术对象、实际问题、数据特征、约束条件、系统架构、目的和教导方向。技术领域标签只是检索线索，不是单独的阻断理由。卫星通信与室内 Wi-Fi、医学影像与自动驾驶等例子必须落到问题和约束的具体差异。

### 需要核实的事实

- D0 的实际技术问题、输入数据、关键约束和评价指标；
- Dk 的实际技术问题、数据、约束、目的和解决方向；
- 两者是否共享可迁移的技术机制、接口和成功标准；
- 是否有文献或公知常识明确指向跨领域迁移，以及迁移后的合理成功预期。

### CombinationPath 与 Ω

记录跨领域迁移的具体节点和操作，不得以“从领域 Y 借用算法”作为完整路径。若迁移需要重定义数据语义、技术对象或评价指标，应在 Δ(p) 中登记。

### 正向闭合与反向断裂

当两文件面对相近问题、处理相同技术数据、共享约束并明确指向同一技术效果时，领域差异不能阻断路径。反向断裂包括问题目的相反、数据和环境不对应、指标不可比、迁移后效果机理不成立或 Dk 存在反向教导。

### 证据与答复动作

TeachingRecord 是本模式核心，须记录“问题—目的—选择方向—明确教导—阻碍因素—成功预期”。EffectEvidenceCard 只采用与目标技术对象和工况相符的比较基准。可以争辩缺乏结合动机或存在阻碍因素，但不得写成“不同技术领域所以必然具备创造性”。

> D0 所解决的是【问题 X】，依赖【数据/对象/约束】并以【指标】评价；Dk 所解决的是【问题 Y】，其教导方向和环境为【具体内容】。现有证据尚未显示从 Y 到 X 的技术迁移操作、接口保持和合理成功预期，因此应将领域差异作为路径分析中的一个约束，而不是单独的法律结论。

## EC-06 技术性与算法—技术对象耦合边界

### 适用与边界

本模式首先处理“是否存在技术方案/技术贡献”的边界争点，再决定是否进入创造性融合分析。输入为具体技术数据、算法与技术对象发生功能性交互并产生客观技术指标时，可形成正向链；仅有抽象数学规则、商业规则、信息展示或在通用计算机上执行而未改变技术对象时，不得把模型名称当作技术贡献。

### 需要核实的事实

- 输入是否来自传感器、接收器、信道、设备状态或其他技术源；
- 算法/模型如何改变技术对象、信号、控制量、存储或网络行为；
- 输出是否可定位到客观技术指标，如信号质量、误码率、时延、功耗、存储或处理器利用率；
- 算法特征与硬件、数据和行为之间是否存在可重放的 S/B→E 因果链。

### CombinationPath 与 Ω

技术性通过后，仍须按 EC-01 至 EC-05 检查多源融合。不得用“技术性成立”替代创造性；也不得在技术性不足时直接进入复杂的组合动机论证。

### 正向闭合与反向断裂

正向链为“具体技术数据 → 受约束算法 → 技术对象控制/功能性交互 → 客观指标”。反向断裂包括输入仅为抽象规则或商业信息、输出仅为信息展示、算法与技术对象没有功能性交互、效果仅为泛化的效率或准确率而无工况和基线。

### 证据与答复动作

EffectEvidenceCard 必须说明指标、比较基准、条件、测量方法和覆盖范围。TeachingRecord 只在已经形成技术事实后说明技术启示和合理成功预期。可就技术性边界争辩、补充技术数据与控制关系，或在原始支持范围内修改；不得把自动评分或相似度作为实体结论。

> 本申请处理的输入是【具体技术数据】，算法步骤【步骤】直接改变【技术对象/控制量】，并在【工况】下影响【客观指标】。该链条与单纯数学运算或信息展示不同；但其创造性仍需另行核验对比文件来源、组合路径和效果因果，不能由技术性结论直接推出。

## 跨模式：整体协同与简单叠加检查

当权利要求含有两组以上区别特征时，另行建立 OverallCooperationCheck，不把它当作第七种模式：

- 分别记录每组特征的 R/F/S/B/E 链；
- 检查特征之间是否共享数据、接口、状态、资源或控制对象；
- 区分“已知模块并列/简单拼接”与“相互支持、相互作用、共同改变技术效果”；
- 若组合效果只在整体结构、时序或约束共同满足时出现，EffectEvidenceCard 必须以整体方案为比较对象；
- 若删除任一组特征仍能独立实现同一效果，不得轻率主张协同效果；
- 中国电学案例材料可作为实践先例提示“模块很多不等于存在协同”，但不能替代案卷事实和法律评价。

## 子领域字段块

### 电子通信与信号处理

按案件需要补充：信号类型、采样率/量化/编码、信道状态、调制方式、帧和协议版本、同步方式、天线/RF/baseband 依赖、误码率、吞吐、时延、功耗和资源预算。

### AI/机器学习

按案件需要补充：训练或推理阶段、输入数据与标签/特征、模型结构和更新方式、训练/推理硬件、输出如何作用于技术对象、指标和比较基线。训练数据本身不是技术效果，必须说明模型输出如何进入技术操作。

### 软件与控制

按案件需要补充：API/服务边界、数据库/缓存/I/O、状态/事件/并发、资源隔离、控制对象、执行主体和单一主体可实施性。软件模块名称不能代替行为、状态和技术效果。

## 资料转化与反过度主张规则

以下资料只用于改进技能的过程对象和证据边界，不直接证明中国法下的创造性结论：

- E-01 Tanaka：可用于五类反驳类型（事实认定、设计事项、结合动机、阻碍因素、有利效果）的分类；其样本主要是 ArgumentOnly，不能外推补正后的授权结果。
- E-02 PARIS/LE-PARIS、E-03 PatRe、E-12 PANORAMA、E-11 Brunner：可用于 OA—答复—结果的多轮轨迹建模，不把流程数据写成技术启示。
- E-04 Schuster/Valentine：引用数量不等于相关性或教导；每篇引用需绑定争点、特征和证据段落。
- E-13 FiNE-Patents：支持“特征—证据段落”锚定，不能替代创造性组合判断。
- E-14 ClaimBrush：只支持补正候选生成；原始支持、版本重建和重算门仍是强制条件。
- 《电学领域专利审查疑难案例评析》：作为实践先例提示同一问题不同原理不当然构成同一教导、简单叠加需区别于相互作用，以及算法须与技术对象和技术指标耦合；不能写成同行评议实证或普遍法规则。

始终避免以下跳跃：

- “分别存在特征” → “能够形成同一工作系统”；
- “工程上可以设计” → “现有技术已经给出到达路径”；
- “不同领域/协议/格式” → “必然没有结合动机”；
- “FusionFeasible=false” → “法律上必然具备创造性”；
- “提高效率/准确率” → “已证明客观技术效果”；
- “引用数量多” → “存在技术启示”；
- “技术性成立” → “创造性成立”。
